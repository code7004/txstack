# 004 — `@txstack/network`

> **한 줄 정의**: axios 확장. **로그와 초기화**를 쉽게 쓸 수 있게 한다.

## 왜 만드는가

새 프로젝트를 시작할 때마다 같은 것을 다시 만든다 — baseURL 설정, 헤더 주입, 에러 처리,
그리고 **"요청이 뭘 보냈고 뭘 받았는지 보이게 하는" 로그**.

이 패키지는 그 두 가지만 잘하면 된다.

1. **초기화** — 한 번의 호출로 쓸 수 있는 클라이언트가 나온다
2. **로그** — 요청·응답·에러를 일관된 형태로 볼 수 있다

**React 에 의존하지 않는다.** Node 스크립트나 서버에서도 쓸 수 있어야 한다.

## 현재 코드 자산

`packages/network/src/`

| 모듈              | 역할                         | 비고                    |
| ----------------- | ---------------------------- | ----------------------- |
| `client.ts`       | 클라이언트 생성              |                         |
| `interceptors.ts` | 인터셉터 (인증 · 401 · 로그) | 범위 재검토 대상        |
| `singleton.ts`    | 전역 인스턴스                | 범위·필요성 재검토 대상 |
| `types.ts`        | 공개 타입                    |                         |
| `utils.ts`        | 유틸                         |                         |

기존 코드는 인증 토큰 주입 · 401 처리 · 응답 봉투(envelope) 해제까지 다룬다.
**요청받은 범위("로그와 초기화")보다 넓다.** 유지할지 잘라낼지 결정해야 한다.

테스트는 `client.test.ts` 1개.

`10_requirements.md` 작성. 그 문서에서 다음을 결정해야 한다.

| 결정할 것                                                                | 왜 먼저 정해야 하나                                                            |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **패키지 범위** — 401 처리 · 응답 봉투 해제를 계속 다루나                | 이건 **런타임 정책**이다. 패키지가 정하면 범용성이 죽는다 (주입으로 갈 것인가) |
| **로그의 형태** — 무엇을 어떤 수준으로 찍나, 끄는 방법, 민감정보 마스킹  | "로그를 쉽게" 가 이 패키지의 절반이다. 형태가 정해져야 구현이 나온다           |
| **초기화 API** — `createClient(options)` 인가, singleton 인가, 둘 다인가 | singleton 은 테스트를 어렵게 만든다. 필요성을 따져야 한다                      |
| **에러 형태** — axios 에러를 그대로 던지나, 자체 에러 타입으로 감싸나    | 소비자 코드의 catch 블록 형태가 여기서 결정된다                                |
| **axios 결합도** — axios 를 감추나 드러내나 (peer 로 둘 것인가)          | 감추면 교체 가능, 드러내면 배우기 쉽다. 둘 다는 안 된다                        |
