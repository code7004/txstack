## 3. 대표 프로젝트

카드 형식: 이름 · 해결한 문제 한 문장 · 본인의 역할 · 기술 일부 · 확인 가능한 링크.

### 3.1 txstack

- **문제:** 여러 서비스가 같은 UI 컴포넌트와 HTTP 설정을 각자 소스 폴더에 복사해 쓰고 있어, 고칠 때마다 서비스마다 다시 고쳐야 했습니다.
- **한 것:** 공통 부분을 어느 서비스의 도메인도 모르는 네 개의 패키지(UI·라우트 메타데이터·훅·HTTP 클라이언트)로 분리했습니다.
  서비스마다 다른 인증·응답 처리 정책은 옵션으로 주입받습니다.
- **역할:** 설계·구현·문서
- **기술:** React · TypeScript · CSS 변수 토큰 · pnpm 모노레포 · Vitest
- **사용처:** 아래 두 플랫폼을 포함한 여러 서비스의 관리 화면(UI·hooks)
- **링크:** GitHub, `/about/case-study`, `/example`

근거: `docs/007_about_draft.md` §1~§5, `CLAUDE.md`

### 3.2 대용량 운영 데이터 분석 플랫폼

- **문제:** 여러 운영사의 사용자·결제 로그가 월 1억 건 이상 쌓이는데 데이터가 흩어져 있고, 운영팀이 통계를 보려면 개발자에게 요청해야 했습니다.
- **한 것:** 원천 DB에서 분석 저장소로 데이터를 증분 수집하는 구조와 집계 API, 운영자가 직접 쓰는 분석 대시보드를 만들었습니다.
  커서 기반으로 수집해 중복 적재를 막고, 중단되어도 이어서 다시 실행할 수 있게 했습니다.
  필터·테이블·URL 쿼리 상태 등 분석 화면은 txstack의 UI와 hooks로 구성했습니다.
- **역할:** 풀스택 — 아키텍처 설계 · 백엔드 · 프론트엔드 · 운영 자동화
- **기술:** React · txstack · Node.js · MySQL · Elasticsearch · AWS
- **규모:** 실제 운영 기준 월 1억 건 이상
- **기간:** 2025.03 ~ 2025.10
- **링크:** 상세 페이지가 생기기 전까지 표시하지 않음

근거: P01 §1~§6, 면접 요약 "주요 경력 축 1"

### 3.3 Terabase — 통합 운영 플랫폼

- **문제:** 외부 BaaS로는 인증·데이터 구조를 세밀하게 바꾸거나 내부 보안 정책을 적용하기 어려웠습니다.
- **한 것:** 인증·데이터(Terastore)·파일 저장(Terabucket)·배포(Terasite)·다국어(Teralocalize) 관리를 자체 인프라 위의 모듈로 나누고, 운영자 화면에서 한곳에서 관리하게 했습니다.
  빌드 결과물을 올리고 버전을 지정하면 서비스에 반영되는 배포 흐름을 만들었습니다.
  운영자 화면은 txstack의 UI와 hooks로 구성했습니다.
- **역할:** 시스템 아키텍처 설계 · 풀스택 개발 · 운영 자동화
- **기술:** React · txstack · Node.js · PostgreSQL · Elasticsearch · Socket.io · AWS S3
- **기간:** 2023.05 ~ 2025.03
- **링크:** 상세 페이지가 생기기 전까지 표시하지 않음

원문의 "완전 대체"·"비용 절감"은 측정 근거가 없으므로 쓰지 않는다.

근거: P02 §1~§7, 면접 요약 "주요 경력 축 2"

### 3.4 품질 기준의 배경 — 의료·재활 소프트웨어 (카드 대신 짧은 문단)

> FDA 승인을 받은 의료·재활 소프트웨어 UINCare(가정용 Home, 병원·센터용 HomePlus)와 RehabMaster에서
> 센서로 환자의 동작을 판정하는 Unity3D 메인 클라이언트를 개발했습니다. 같은 동작에는 반복해도
> 같은 판정이 나와야 했고, 센서 오류가 환자 안전에 영향을 주지 않도록 방어적으로 설계해야 했습니다.
> FDA 승인 절차에 맞춰 요구사항·설계·구현·검증을 문서로 잇는 V-Model 방식으로 일하며 클라이언트의 설계·검증 문서에 대응했고, 이 경험이 지금도 상태 표현과
> 예외 흐름, 변경 이력을 먼저 보는 기준이 되었습니다.

원문 P05의 "FTA"는 FDA의 오기다. 승인 절차에서 본인이 맡은 범위는 클라이언트 개발과 그에 따른 검증 대응이다.

근거: 이력서 "유인케어", P05 §3~§5

## 4. 경험이 txstack으로 이어지는 과정 (`PROFILE.why`)

> 여러 관리 화면을 개발하면서 같은 폼과 목록, 라우트와 메뉴 설정을 반복해서 만들었습니다.
> 서비스마다 복사해 둔 코드는 조금씩 달라졌고, 한 곳을 고치면 다른 곳도 찾아 고쳐야 했습니다.
>
> 그래서 공통 기능과 서비스 정책을 나누기로 했습니다. 토큰을 어디서 읽고 401에 무엇을 할지는 앱이 정하고,
> 라이브러리는 그 정책을 받아 실행합니다. 기준은 하나입니다. 다음 프로젝트가 설치만으로 그대로 쓸 수 있는가.

| 반복되던 문제                      | 사이트에서 확인할 결과                                      |
| ---------------------------------- | ----------------------------------------------------------- |
| 라우트와 메뉴 정의를 따로 관리     | `/docs/guide/routing` — 트리 하나에서 라우터·메뉴·현재 위치 |
| 입력·목록·피드백 UI를 반복 작성    | `/docs/components`, `/example`                              |
| 서비스마다 다른 인증·응답 처리     | `/docs/guide/http-client`                                   |
| 저장소 안에서만 동작하는 공통 코드 | `/about/case-study` — `.tgz`를 별도 소비자 앱에 설치해 검증 |

과거 프로젝트와의 관계: 이전 프로젝트들은 txstack의 UI와 hooks를 소스 폴더(`src/@core/`)에 포함해 실제로 썼다.
분석 플랫폼 포트폴리오의 `TxDropdown`·`TxCoolTable`이 그 예다. 공개 문구에는 이렇게 덧붙인다.

> 데이터 분석 플랫폼과 Terabase의 관리 화면은 txstack의 UI와 hooks로 만들었습니다. 그때는 각 서비스의
> 소스 폴더에 포함해 썼고, 지금은 이를 독립 패키지로 나누고 라우트 메타데이터·HTTP 클라이언트를 더해
> 설치만으로 쓸 수 있게 정리하고 있습니다.

근거: `docs/007_about_draft.md` §1·§3, P01 §6 "커스텀 UI & 상태 관리", `CLAUDE.md` "프로젝트 개요"

## 6. 개발·협업 방식과 기술

### 6.1 일하는 방식

- 사용자가 보는 화면과 데이터가 처리되는 흐름을 함께 살펴봅니다.
- 반복되는 문제는 공통 구조로 정리하고, 서비스별 정책은 분리합니다.
- 정상 동작뿐 아니라 실패·재시도·복구와 운영 이력을 고려합니다.
- 설계 이유와 검증 결과를 남겨 다음 변경을 판단할 근거를 만듭니다.

AI 도구 활용은 Profile에서 다루지 않는다.

근거: 010 §4.6, `CLAUDE.md` "절대 규칙", 면접 요약 "핵심 이미지"

### 6.2 기술 (`PROFILE.skills`, 묶음별)

- **현재 주요 영역:** React · TypeScript · 공통 UI 구조 · 라우팅 · URL 상태 · React Query · Redux · Vite · Webpack · Tailwind · Sass
- **서버·데이터·운영:** Node.js · NestJS · Koa · PostgreSQL · MySQL · Elasticsearch · Socket.io · AWS
- **확장 경험:** Vue.js · React Native · WebAssembly/WebGL · Unity/C# · V-Model · IEC 62304
