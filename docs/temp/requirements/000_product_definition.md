# 000. 제품 정의 — 이 라이브러리 세트는 무엇이고 왜 이렇게 나뉘는가

- 로드맵: [ROADMAP](../ROADMAP.md)
- 상태: **§1~§3 확정 (2026-08-19)** — 4개 패키지의 존재 이유와 분할 근거가 모두 기록됨
- 최종 갱신: 2026-08-19

## 이 문서가 있는 이유

`001` 은 "원본 3개 저장소의 `src/core` 를 뽑아낸다" 였다. **왜 4개로 나누는가, 각각이 왜 필요한가는
논의된 적이 없다.** 추출의 결과로 4개가 됐을 뿐이다.

모든 트랙(0~9)의 판단이 여기서 정한 것에 걸린다. 무엇을 남기고 무엇을 걷어낼지, 어디까지 다듬을지가
"누가 쓰는가" 와 "이 패키지가 왜 존재하는가" 로 결정되기 때문이다.

---

## 1. 소비자와 포지셔닝

### 1-1. 설계 기준은 "진짜 공개 범용"

도메인 지식 0, 앱 전역 가정 0, 시맨틱 버전 준수. 모르는 사람이 설치해도 동작해야 한다.

이건 선택이 아니라 **필수 조건**이기도 하다. 원본 3개 저장소가 복사본을 공유하려면 어차피
어느 한 앱에 종속되면 안 된다.

### 1-2. 그러나 성공 기준은 채택 수가 아니다

**"MUI 보다 좋은 것을 만든다" 는 목적이 아니다.** 인력 1명으로 27종을 접근성·커버리지까지 붙여
기성 라이브러리를 이기는 것은 불가능하고, 이기려 할 이유도 없다.

| 항목      | 기준                                                                                  |
| --------- | ------------------------------------------------------------------------------------- |
| 설계 기준 | 공개 범용 — 도메인 0, 앱 가정 0                                                       |
| 성공 기준 | **"모르는 사람이 설치해서 막히지 않는다"** — 3개 저장소 공유는 결과이지 목표가 아니다 |
| 경쟁 태도 | 기성 라이브러리를 대체하려 하지 않는다. **다른 트레이드오프를 제공한다**              |

### 1-3. 판단이 갈릴 때의 기준

| 상황                            | 판단                                                                    |
| ------------------------------- | ----------------------------------------------------------------------- |
| 라인업이 비어 보인다            | **채우지 않는다.** 실제 요구가 있을 때만 만든다                         |
| 기성 라이브러리에 있는 기능이다 | 그것만으로는 만들 이유가 되지 않는다. **우리 트레이드오프**가 있을 때만 |
| 특정 백엔드·앱 규약이 필요하다  | **넣지 않는다.** 프로젝트로 내보낸다                                    |
| 편의를 위해 정책을 정해야 한다  | 정책의 **모양까지** 라이브러리가 정하는지 본다. 그렇다면 빼낸다         |
| 유지 비용이 값어치를 넘는다     | 뺀다. 코드가 작다는 것은 남길 이유가 되지 않는다                        |
| 기존 저장소가 이렇게 쓰고 있다  | **근거가 되지 않는다.** 원본은 복사본이었다 (§1-4)                      |

> **"주입 가능하게 만들었으니 종속이 아니다" 는 함정이다.**
> 슬롯의 모양 자체가 전제를 담는다. 값만 채우게 하는 것과 형태를 소비자가 정하는 것은 다르다.
> 이 함정에 `@txstack/network` 가 걸렸다 (§2-2).

---

### 1-4. 기존 3개 저장소와의 호환은 제약이 아니다 (2026-08-19 확정)

**원본이 이렇게 쓰고 있다는 사실은 API 를 그대로 두어야 할 근거가 되지 않는다.**

원본은 `src/core` 복사본이었다. 복사본 시절의 이름과 형태를 라이브러리가 물려받을 이유가 없다.
지금 고치지 않으면 **소비자 전체가 그 불일치를 영구히 떠안는다.**

| 무엇                        | 방침                                                                |
| --------------------------- | ------------------------------------------------------------------- |
| 원본의 호출부가 깨지는 변경 | **한다.** 역이식(9-3)에서 고친다                                    |
| 원본 사용량 실측            | **계속 쓴다.** 다만 "지켜야 할 계약" 이 아니라 **"쓸모의 증거"** 로 |
| 전환 비용(N개 파일)         | 근거로 **세지 않는다**                                              |
| 원본에만 있는 관례          | 생태계 표준과 어긋나면 **버린다**                                   |

> **사용량 실측이 무의미해지는 것이 아니다.** 아무도 안 쓰는 것은 여전히 만들 이유가 없다는 증거다
> (`useSafePolling` 2건 → 제거). 바뀌는 것은 **"많이 쓰이니 이름을 못 바꾼다"** 는 논리뿐이다.

#### 이 결정이 여는 것

호환을 지키느라 미뤄 두었던 정비가 가능해진다. 실측된 불일치:

| 같은 의미      | 갈린 이름                                                                                    |
| -------------- | -------------------------------------------------------------------------------------------- |
| 숫자 변경 콜백 | `onChangeNumb`(TxDropdown) · `onChangeNumber`(TxInput) · `onChangeInt` · `onChangeFloat`     |
| 텍스트 변경    | `onChangeText`(TxInput·TxDropdown) vs **`onChangedText`**(TxTextarea) — 과거형 `d` 하나 차이 |
| 닫기           | `onExit`(TxModal) vs `onClose`(TxSlidePanel)                                                 |
| 제출           | `onSubmitNumber` · `onSubmitNumb` · `onSubmitNums` · `onSubmitBool` · `onSubmitValue`        |

소비자는 컴포넌트마다 콜백 이름을 외워야 한다. **이것이 "얇은 통제권"(§2-1)의 값어치를 깎는다** —
배울 것이 적다는 것이 이 라이브러리의 판매 논거인데, 이름이 갈리면 그 논거가 약해진다.

정비는 트랙 1-1 C절에서 한다.

#### 역이식(9-3)의 성격이 바뀐다

기존 계획은 "기계적 치환" 이었다. 이제는 **실질적인 리팩터링**이다.
그 비용은 라이브러리 품질과 맞바꾼 것이며, **한 번만 치르면 된다.**

## 2. 패키지별 존재 이유

### 2-1. `@txstack/ui` — **포지셔닝 · 정리 확정 (2026-08-19)**

#### 무엇을 파는가

기성 컴포넌트 라이브러리(MUI · shadcn · Radix)를 **대체하려 하지 않는다.**
인력 1명으로 27종을 접근성·커버리지까지 붙여 이기는 것은 불가능하고, 이기려 할 이유도 없다.

파는 것은 **얇은 통제권**이다 — 커스터마이즈 제약이 없고, 배울 것이 적고, 남의 로드맵에 끌려다니지 않는다.

#### 근거를 실측으로 정정한다

원본 3개 저장소에서 커스터마이즈 수단의 실사용을 셌다.

| 수단         | 사용        |
| ------------ | ----------- |
| `className=` | **1,825회** |
| `theme={`    | 47회        |

`Tx*` 사용이 총 1,177회이므로 **`theme` 은 4%에서만 쓰인다.** 그 47회의 내용도 예상과 달랐다.

```tsx
theme={{ wrapper: "", focus: "" }}            // ← 빈 문자열
theme={{ caption: "text-red-200 bg-red-200" }}
```

**주력 용도가 "기본 스타일을 끄는 것"** 이다. 테마를 갈아입히는 것이 아니라 방해되는 기본값을
지우는 탈출구로 쓰인다.

따라서 가치 서술을 이렇게 정정한다.

> Tailwind 클래스를 그대로 얹을 수 있고(`className`), 기본 스타일이 방해되면 끌 수 있다(`theme: ""`).
> MUI 의 `sx`/theme override 같은 **별도 추상을 배우지 않는다**는 것이 실제 차이다.

| 파는 것                     | 근거                                                       |
| --------------------------- | ---------------------------------------------------------- |
| 앱과 같은 어휘로 스타일링   | 테마가 Tailwind 클래스 문자열이다. 새 추상이 없다          |
| 방해되면 끌 수 있다         | `theme: { key: "" }` 로 기본 클래스를 비운다 (실사용 주력) |
| specificity 싸움이 없다     | 런타임 CSS 를 만들지 않는다                                |
| 남의 로드맵에 안 끌려다닌다 | 전부 우리 코드다                                           |

정직하게 적어두는 비용 — 접근성이 Radix/MUI 대비 약하다(포커스 트랩 없음, 키보드 조작 미검증).
커버리지가 얇다(Toast · Popover · Autocomplete 없음). 유지 인력이 1명이다.

> ⚠ **`theme` 이 4%라는 숫자를 "theme 은 불필요하다" 의 근거로 쓰면 안 된다.**
> 원본 3개는 `core/tx-ui` 가 **복사본이라 언제든 직접 고칠 수 있었다.** npm 패키지가 되면
> 그것이 불가능해지므로 `theme` 의 중요도는 오히려 **올라간다.**

#### 결정 — 컴포넌트 2종 제거

사용량과 크기를 함께 놓고 판정했다.

| 컴포넌트                | 줄        | 원본 사용 | 판정                              |
| ----------------------- | --------- | --------- | --------------------------------- |
| **`TxCoolTable`**       | **1,024** | 3         | **제거** — 패키지 소스의 18%      |
| **`TxClipboardButton`** | **5**     | **0**     | **제거** — 컴포넌트라 하기 어렵다 |

**`TxCoolTable`** — 이미 `@deprecated` 이고, **같은 패키지 안에 대체재(`TxAgGrid`)가 있다.**
"쓰는 사람이 적은 범용 컴포넌트" 와 다르다. 제거하면 `001-2` I8(렌더마다 찍히는 deprecation 경고)도
함께 사라진다.

**`TxClipboardButton`** — 내용이 `<div onClick={copy}>📋</div>` 가 전부다. `button` 요소가 아니라
키보드로 접근할 수 없고, 이모지가 하드코딩돼 있으며, 성공/실패 피드백이 없다.
컴포넌트라기보다 **미완성 조각**이다.

둘을 빼면 **1,029줄(18%)** 이 줄어든다.

#### 결정 — 사용량이 낮아도 유지하는 것들

`TxLayout`(4) · `TxContextMenu`(2) · `TxTabs`(3) 는 **유지**한다.

`network` · `hooks` 와 판정이 다른 이유 — 거기서는 **"공유될 수 없는 것"** 이 문제였다.
여기서는 3개 앱이 안 쓸 뿐이고 **범용 UI 프리미티브로는 정상**이다.
컴포넌트 라이브러리에 모든 앱이 쓰는 컴포넌트만 있을 이유는 없다.

#### 열어둔 질문

**`theme` 시스템의 비용/편익.** `themeMerge` · `DeepPartial` · merge/override 정책이 27종 전 파일에
붙어 있는데 4%에서만 쓰이고 주용도가 "끄기" 다. 끄기가 주력이라면 `unstyled` 같은 더 단순한 API 가
나을 수도 있다.

**지금 결론 낼 문제가 아니다.** 위 반론(패키지가 되면 중요도 상승) 때문에, 실제 소비 경험이
쌓이는 1-3(고도화)에서 판단한다.

### 2-2. `@txstack/network` — **축소 확정 (2026-08-19)**

#### 원래 의도

보일러플레이트 감소 · 로그 강화 · 에러 핸들링.

#### 대조 결과

세 의도는 코드에 실재했다. 그러나 **대부분이 "주입 가능한 형태로 포장된 프로젝트 종속"** 이었다.

| 요소                                     | 담고 있던 전제                         |
| ---------------------------------------- | -------------------------------------- |
| `unwrap`                                 | 서버가 응답 봉투를 쓴다                |
| `getToken` · `authHeader` · `authScheme` | 인증이 헤더 토큰 방식이다              |
| `onUnauthorized`                         | 401 이 로그아웃 신호다                 |
| `IApiError`                              | 에러가 NestJS 형태다                   |
| `IApiResponse`                           | 페이지네이션이 limit/offset/total 이다 |
| `withCredentials: true` 기본값           | 쿠키를 함께 보낸다                     |
| 싱글턴 6종                               | 앱에 클라이언트가 하나다               |

정책을 주입받는다고 적혀 있었지만, 실제로는 **정책의 모양을 라이브러리가 정하고 소비자는 값만
채우는** 구조였다. §1-3 의 함정에 정확히 걸린 사례다.

추가로 드러난 자기모순:

- `unwrap`(성공 응답 형태)은 주입받으면서 **에러 응답 형태는 하드코딩**했다 — 비대칭
- 로그 목적지가 `console` 로 고정이라 Sentry·서버 로거로 못 보낸다 — "정책을 정하지 않는다" 위반
- 공개 export 11개 중 **6개가 싱글턴**인데, JSDoc 은 "신규 코드에서 쓰지 않는다" 고 적혀 있다

#### 결정 근거

**원본 3개 저장소의 백엔드 규약이 서로 다르다** (사용자 확인, 2026-08-19).
봉투·인증·401 은 애초에 공유될 수 없는 것이었다. 공유 가능한 것만 남긴다.

#### 결정: axios **플러그인 모음**으로 축소한다

HTTP 클라이언트를 자처하지 않는다. 클라이언트는 소비자가 `axios.create` 로 만들고,
프로젝트 무관하게 반복되는 두 가지만 이 패키지가 제공한다.

**남기는 것**

| 대상          | 왜 범용인가                                                                            |
| ------------- | -------------------------------------------------------------------------------------- |
| 로깅 인터셉터 | 소요 시간 측정 · 민감 필드 마스킹 · 그룹 로그. 백엔드 규약과 무관하게 매번 손으로 짠다 |
| 에러 정규화   | `http` / `network` / `timeout` / `canceled` 판별. axios 를 쓰는 누구나 겪는다          |

**걷어내는 것**

`createHttpClient` · `HttpClient` · `unwrap` · `getToken` · `authHeader` · `authScheme` ·
`onUnauthorized` · 싱글턴 6종 · `IApiResponse` · `IApiError` · `removeUndefined` · `isTokenExpired`

11개 export → 3~4개.

**축소 후 소비자 코드**

```ts
const api = axios.create({ baseURL: "/api" });

attachRequestLogger(api, { logger: console, maskFields: ["password"] });

// 봉투·인증·401 은 소비자가 자기 인터셉터로 — 프로젝트마다 어차피 다르다
api.interceptors.request.use((c) => {
  c.headers.set("Authorization", `Bearer ${getToken()}`);
  return c;
});
```

**폐기하지 않은 이유** — 폐기하면 마스킹·소요시간 로깅이 3개 저장소에서 다시 갈라진다.
그것이 이 프로젝트를 시작한 문제 그 자체다. 로깅과 에러 판별만 남기면 종속은 0 이 되면서
그 문제는 막힌다.

### 2-3. `@txstack/hooks` — **축소 · API 재설계 확정 (2026-08-19)**

#### 원본 실사용

| 훅                                          | 줄  | black-message | usertics | chain-wallet | 합계   |
| ------------------------------------------- | --- | ------------- | -------- | ------------ | ------ |
| `useUrlQuery`                               | 268 | 2             | **31**   | 2            | **35** |
| `useStateForObject` (구명 `useUpdateState`) | 65  | 6             | 15       | 14           | **35** |
| `useObjectChanged`                          | 66  | 0             | 4        | 0            | 4      |
| `useSafePolling`                            | 51  | 0             | 0        | 2            | 2      |

남길 둘이 뺄 둘보다 **9~17배** 많이 쓰인다.

#### 결정 1 — 훅 2종만 남긴다

**유지** — `useStateForObject` · `useUrlQuery`
**제거** — `useSafePolling`(2건) · `useObjectChanged`(4건)

각 훅의 존재 이유:

| 훅                  | 무엇을 해결하나                                                                    |
| ------------------- | ---------------------------------------------------------------------------------- |
| `useStateForObject` | 객체 상태를 부분 갱신한다. `setObj({...obj, a: 10})` 대신 `setObj({ a: 10 })`      |
| `useUrlQuery`       | URL 쿼리(`?a=10&b=apple&c=true`)를 객체로 오가게 한다. `searchParams` 의 편의 버전 |

#### 결정 2 — `useUrlQuery` 의 API 를 대폭 좁힌다

원본에서 옵션별 실사용을 세어 보니 예상과 달랐다.

| 옵션         | 사용    | 처리                                                     |
| ------------ | ------- | -------------------------------------------------------- |
| `urlKeys`    | 28건    | **제거** (아래 참조)                                     |
| `postParse`  | 25건    | 유지                                                     |
| `encode`     | 4건     | 유지                                                     |
| `replace`    | 4건     | 유지                                                     |
| `queryTypes` | 3건     | **제거** — 기본값의 `typeof` 로 런타임이 타입을 알아낸다 |
| `afterParse` | **0건** | **제거** (이미 deprecated)                               |

> **`urlKeys` 를 제거하는 이유** — 구현은 "키를 **추가**" 인데, 28건의 실사용은
> "URL 에 실을 키를 **고른다**" 로 쓰고 있었다. 예: `defaults` 에 `keyword` 가 이미 있는데
> `urlKeys: ["keyword"]` 를 또 지정한다(무효). **API 가 오해를 부르고 있었다는 신호다.**
> 새 API 에서는 `defaults` 가 곧 타입이라 키 추가라는 개념 자체가 성립하지 않는다.

**새 시그니처** — 기본값을 래핑 없이 첫 인자로 받는다.

```ts
export function useUrlQuery<T extends object>(defaults: T, options?: UseUrlQueryOptions<NoInfer<T>>): [T, UrlQuerySetter<T>];

export interface UseUrlQueryOptions<T> {
  postParse?: (query: Partial<T>) => Partial<T>;
  replace?: boolean;
  encode?: boolean;
}
```

```ts
useUrlQuery({ a: 10, b: "apple" }); // 추론
useUrlQuery<{ a: number; b: string }>({ a: 10, b: "apple" }); // 명시
useUrlQuery({ page: 1 }, { postParse: (q) => ({ offset: ((q.page ?? 1) - 1) * 20 }) });
```

`NoInfer` 를 2번 인자에 거는 구조라, **추론이 1번 인자 한 곳에서만 일어난다.**
2026-08-19 에 고친 추론 붕괴 결함이 구조적으로 재발할 수 없다.

#### 결정 3 — 기성 라이브러리(nuqs) 대신 유지하는 근거

[§1-3](#1-3-판단이-갈릴-때의-기준) 의 기준은 "기성 라이브러리에 있는 기능만으로는 만들 이유가
되지 않는다. 우리 트레이드오프가 있을 때만" 이다. API 를 좁힌 결과 트레이드오프가 분명해졌다.

```ts
useQueryStates({ a: parseAsInteger.withDefault(10), b: parseAsString.withDefault("apple") }); // nuqs
useUrlQuery({ a: 10, b: "apple" }); // txstack
```

- **값에서 타입이 나온다.** 키마다 파서를 선언하지 않는다
- **의존이 0 이다.** `react-router-dom` peer 외에 추가 설치·어댑터 설정이 없다
- `postParse` 로 파생값 보정이 훅 안에서 끝난다 (25건 사용)

전환 비용(35개 파일)도 유지 쪽 근거지만, 그것만으로는 근거가 되지 않는다고 본다.

#### 결정 4 — 패키지를 나누지 않는다

훅별 분리는 **의존 프로파일이 다를 때** 의미가 있는데, 그건 이미 subpath(`@txstack/hooks/router`)로
해결돼 있다. 훅 2개에 패키지 2개면 버전·README·changeset·배포가 2배가 되고 얻는 것이 없다.

패키지는 **유지**한다. `useUrlQuery` 가 nuqs 대비 분명한 우위를 갖게 되었으므로,
"65줄짜리 훅 하나만 남아 패키지가 성립하지 않는" 시나리오는 발생하지 않는다.

#### 열어둔 질문

  `postParse` · shallowEqual 리렌더 차단 · 함수형 patch 다. 이것들이 "각자 쓰면 안 되는 이유" 가
  될 만큼 강한지는 2-1 에서 다시 본다.
- 라우터 어댑터를 열어 Next.js·TanStack Router 소비자를 받을지 (2-3)

### 2-4. `@txstack/route-meta` — **API 방향 확정 (2026-08-19)**

#### 원래 목적 (사용자 진술)

1. react-router-dom 의 라우터 리스트만으로 부족한 것을 **메타 방식으로 추가**
2. 페이지 컨트롤 · 설명 · icon
3. **GNB · 하위 메뉴**를 쉽게 구현
4. **페이지 이동을 path 문자열이 아니라 변수로** 관리

#### 원본 3개 저장소 실측

원본이 이 PC 에 있어 직접 확인했다 (`/w/Projects/{black-message,usertics,chain-wallet-service}`).

**두 세대가 존재한다.** usertics 는 `ExRouteObject extends Omit<RouteObject, "children">` 로
`name`·`icon`·`disable`·`permisions`(숫자 배열)를 **최상위 필드**에 두는 구세대다.
black-message / chain-wallet 이 `meta` 로 분리한 현세대이고, 패키지는 이쪽을 가져왔다.

| 항목                    | black-message | usertics  | chain-wallet  |
| ----------------------- | ------------- | --------- | ------------- |
| 노드 수                 | 36            | 44        | 52            |
| `meta.description`      | 0             | 5         | **52 (전체)** |
| `meta.icon`             | 0             | 44 (전체) | **52 (전체)** |
| `meta.onClick`          | 0             | 0         | **0**         |
| **동적 경로(`:param`)** | **0**         | **0**     | **0**         |

- `description` · `icon` 은 실제로 쓰인다 → 유지
- **`meta.onClick` 은 세 저장소 어디서도 안 쓴다** → 제거 후보
- **동적 경로가 한 건도 없다** → `to(path, { id })` 같은 파라미터 헬퍼가 불필요. 설계가 크게 단순해진다

#### 목표별 대조

| 목표               | 결과                                                       |
| ------------------ | ---------------------------------------------------------- |
| 1. 메타 추가       | ✅ 달성. `meta` 가 실행 계층으로 전달되지 않는 분리도 명확 |
| 2. 설명 · icon     | ✅ 달성. `meta.onClick` 만 사문화                          |
| 3. GNB · 하위 메뉴 | ⚠️ **절반.** 패키지는 데이터만 준다 (§아래)                |
| 4. path 를 변수로  | ⚠️ 성립하지만 **취약하다** (§아래)                         |

**목표 3 이 절반인 이유** — `getNavigableRoutes` 는 필터된 데이터만 돌려주고, 실제 메뉴 컴포넌트는
세 앱에 각자 남아 있다. black-message `LayoutGNB`(80줄, 하위 메뉴 컬럼 정렬 트릭 포함),
usertics `GNB` + `SideNavBar`(접기/펴기, 아이콘 자리 확보). "쉽게 구현"의 어려운 부분이 전부 앱에 있다.

#### 발견한 결함 — `RouteTree` 타입 주석이 목표 4를 깨뜨린다

`RouteTree = Record<string, RouteNode>` 이므로, **타입 주석으로 붙이면 리터럴 키가 사라진다.**
tsc 로 확인했다:

```ts
const A: RouteTree = { dashboard: { path: "/dashboard" } };
A.dashboarrrd; // ❌ 오타가 안 잡힌다 (Record<string, …> 이므로 어떤 키든 유효)

const B = { dashboard: { path: "/dashboard" } } satisfies RouteTree;
B.dashboarrrd; // ✅ TS2551 "Did you mean 'dashboard'?"
```

black-message 원본은 주석 없이 선언해 **우연히** 살아 있고,
**우리 playground 예제는 `: RouteTree` 를 붙여 목표 4를 깨뜨리고 있다.**
패키지 어디에도 "주석 대신 `satisfies` 를 쓰라" 는 안내가 없다.

#### 결정 1 — 경로 맵은 **계층형**으로 간다

세 형태를 만들어 TypeScript 컴파일러에 **go-to-definition(F12) 이 어디에 착지하는지 직접 물었다.**

| 형태                         | 자동완성 | 오타 검출 | **F12 추적**           |
| ---------------------------- | -------- | --------- | ---------------------- |
| **A. 계층형** (`.$`)         | ✅       | ✅        | ✅ 원본 선언으로 착지  |
| B. 평탄형                    | ✅       | ✅        | ❌ **아무 데도 안 감** |
| C. `children` 투명 (`.path`) | ✅       | ✅        | ✅ 원본 선언으로 착지  |

**평탄형은 추적이 되지 않는다.** 평탄화가 `UnionToIntersection`(조건부 타입 + `infer`)을 거치면서
원본 선언과의 연결이 끊긴다. 자동완성 목록에는 뜨지만 F12 가 이동하지 않는다.
`[K in keyof T]` 형태(homomorphic mapped type)만 선언 링크를 보존한다.

**A(계층형)로 확정한다.** 사용자의 초기 의도 형태이며 추적이 보장된다.

```ts
paths.Contents.BlackUsers; // "/black"      리프는 문자열 그대로
paths.Contents.Dashboard.$; // "/dashboard"  중간 노드는 예약 키 `$` 로 자기 경로
paths.Contents.Dashboard.DashboardSearch; // "/dashboard/search"
```

> **비용** — 자식이 있는 노드는 문자열이면서 동시에 객체일 수 없으므로 `.$` 가 붙는다.
> `String` 객체로 둘 다 되게 하는 트릭은 `navigate()` 가 `typeof to === "string"` 을 보기 때문에
> 런타임에서 깨진다. 실사용에서 `.$` 가 거슬리면 C 로 바꾸는 것은 타입 한 줄 교체다.

값 타입은 리터럴이 아니라 `string` 으로 넓어진다 (`RouteNode.path?: string` 때문).
동적 경로가 0건이라 실용상 문제 없다. 리터럴이 필요해지면 `as const` 를 추가로 요구한다.

#### 결정 2 — **팩토리 + 훅.** 리터럴 보존이 전제다

패키지가 독립적인 `useRoutePath()` 를 export 하면 **앱의 트리 타입을 알 수 없어** 반환 타입이
`RouteTree` 로 뭉개진다. 그러면 결정 1이 통째로 무너진다.

따라서 **소비자의 트리를 통과시키는 팩토리**가 타입이 붙은 훅을 만들어 내보낸다.

```ts
// app/routes.ts
export const { routes, paths, useRoutePath } = createRoutes({
  Contents: { path: "/", children: { Dashboard: { path: "/dashboard", meta: { label: "대시보드" } } } }
});
```

- 제네릭 추론이 걸리므로 소비자가 **타입 주석을 붙일 일 자체가 없다** → `satisfies` 함정이 사라진다
- `paths` 는 값이라 컴포넌트 밖(라우터 가드·유틸)에서도 쓴다
- `useRoutePath()` 는 그 값을 돌려주는 sugar 다. 훅으로만 제공하지 않는 이유는, 훅으로 강제하면
  컴포넌트 밖에서 못 쓰기 때문이다

#### 결정 3 — GNB · SideNavBar 는 패키지에 넣지 않는다

세 저장소의 메뉴 구현이 서로 많이 다르다 (드롭다운형 GNB / 접히는 사이드바 / 하위 메뉴 컬럼 정렬).
**프로젝트마다 커스텀이 강한 영역**이므로 컴포넌트로 고정하지 않고, **문서에 다양한 예제**로 해결한다.

패키지는 `getNavigableRoutes` 로 데이터를 주는 데까지만 한다. 목표 3 은 "라이브러리가 메뉴를
그려준다" 가 아니라 **"메뉴를 그리기 쉬운 데이터를 준다"** 로 재정의한다.

### 3-2. 그러나 크기가 아니라 **의존 프로파일**이 결정한다

**`peerDependencies` 는 패키지 단위라 subpath 로 피할 수 없다.** 프로파일이 다르면 나누는 것 말고 방법이 없다.

### 3-3. 유지 비용을 과대평가했었다 — 정정

이 문서 초안은 "4개로 나누면 버전 4개 · README 4개 · changeset 4개 · **배포 4번**의 유지 비용이
영구히 붙는다" 고 적었다. **과장이다.**

- `pnpm changeset` 은 한 번에 여러 패키지를 고른다
- `changeset publish` 는 **한 번에 전부** 배포한다. 4번이 아니다
- 버전이 갈리는 것은 오히려 **장점**이다 — `network` 만 고쳤는데 `ui` 소비자가 버전업 알림을 받지 않는다

실제 비용은 README 4벌뿐이고, 합쳐도 섹션 4개는 필요하다.

### 3-4. 결정 — **4개 유지**

크기가 작다는 것은 합칠 이유가 되지 않는다. 나누는 근거는 의존 프로파일이고, 그것이 네 갈래로 갈린다.

### 3-5. 이 검토가 드러낸 결함 — `ui` 가 라우터에 묶여 있다

**`@txstack/ui` 가 `react-router-dom` 을 필수 peer 로 강제한다.**

```
packages/ui/src/TxCard/TxCard.tsx:2                 import { Link } from "react-router-dom"
packages/ui/src/TxContextMenu/TxContextMenu.tsx:3   import { NavLink } from "react-router-dom"
packages/ui/src/TxDropMenu/TxDropMenu.tsx:3         import { NavLink } from "react-router-dom"
```

**25종 중 3종 때문에 UI 라이브러리 전체가 React Router 에 묶인다.**
Next.js · TanStack Router 소비자는 `@txstack/ui` 를 설치조차 할 수 없다.

§1-1 에서 "진짜 공개 범용" 을 기준으로 정했으므로 **포지셔닝과 정면으로 어긋난다.**
ag-grid · react-day-picker 는 subpath 로 격리했으면서 정작 라우터는 코어에 박혀 있다.

게다가 세 곳 모두 **선택적 기능**이다 — `TxCard` 의 `link` prop, `TxDropMenu.LinkItem`,
`TxContextMenu` 옵션의 `to`. 안 쓰면 그만인 기능 때문에 전 소비자가 라우터를 설치한다.

#### 결정 — Link 컴포넌트 주입 (A안)

`TxThemeProvider` 에서 `linkComponent` 를 받아 세 컴포넌트가 그것을 쓴다.
소비자 설정은 **한 번**이면 된다.

```tsx
// 소비 앱 (react-router)
import { Link } from "react-router-dom";
<TxThemeProvider linkComponent={Link}>...</TxThemeProvider>;

// 소비 앱 (Next.js)
import Link from "next/link";
<TxThemeProvider linkComponent={Link}>...</TxThemeProvider>;

// 라우터를 안 쓰면 지정하지 않는다 → 세 기능이 <a> 로 폴백하거나 비활성
```

대안이었던 것 — prop 주입(`linkAs`)은 호출부마다 넘겨야 해서 번거롭고,
기능 제거(`href` + `onClick`)는 SPA 내비게이션 의미를 잃는다.

조치 후 `react-router-dom` 은 `@txstack/ui` 의 peer 에서 **빠진다**.
이는 **배포 전 필수**이며 트랙 1-1 에서 처리한다 (1-3 은 배포 게이트에 들어가지 않는다).

### 3-6. 함께 기록하는 안건 — `@txstack/network` 개명

축소 후 이 패키지는 **150줄짜리 axios 플러그인 2종**이다. HTTP 클라이언트가 아니다.
그런데 이름이 `network` 라 클라이언트를 기대하고 설치할 사람이 있다.

미배포라 개명 비용이 0 이다. 트랙 4-1 에서 판단한다.
