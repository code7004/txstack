# UI·라우트 설정의 사용 편의성과 사이트 전달력 검수

> 검수일: 2026-10-22 · 대상: https://code7004.github.io/txstack/ 및 현재 저장소
> 목적: UI와 라우트를 쉽게 설정한다는 장점이 구현과 사이트에서 충분히 전달되는지 확인한다.
> 앱·패키지는 수정하지 않았다. 이 문서는 관찰·판단·후속 작업 제안을 구분한 보고서다.

## 1. 결론

**UI와 route-meta의 기반은 좋고, 사이트에도 대표 기능이 실제로 표현되어 있다.
부족한 것은 기능의 존재보다 ‘내 프로젝트에서도 쉽게 시작할 수 있다’는 것을 보여 주는 과정이다.**

홈의 ‘관리 화면을 만드는 React UI와 도구’라는 제목과 짧은 설명은 명확하다.
route 설정 변경이 GNB·사이드바·브레드크럼에 반영되는 시연은 이 프로젝트의 대표 강점이다.
다섯 패키지를 같은 비중으로 더 설명하는 대신 **UI 조립과 route 설정을 두 개의 대표 사용 경로**로
앞세우고, 나머지 패키지는 그 작업을 돕는 도구로 안내하는 편이 목적에 맞는다.

대규모 재설계나 새로운 공개 API 추가를 권하지 않는다. 기존 데모·가이드·예제를 재사용해
**실물 → 최소 코드 → 실행 가능한 예제**를 가깝게 붙이는 것이 우선이다.

## 2. 확인 방법과 한계

### 직접 확인

- 배포 홈의 제목·설명·주요 행동·UI 기능군·route 시연·테마 체험·패키지 안내
- 홈 route 시연의 메뉴 추가, 이름 변경, 뷰어 전환
- 배포 Getting Started 이동과 설치 안내, Routing & Menu 가이드 접근
- 넓은 화면과 390×844 모바일 화면의 배치
- 라우팅 가이드에서 수집된 브라우저 오류 로그: 조회 시 오류 없음
- 현재 홈·UI 시연·라우트 시연·가이드·패키지·CI·소비자 검증 코드

### 실행한 검사

| 항목              | 결과                                                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm build`      | 5개 패키지 빌드 통과                                                                                                             |
| `pnpm check`      | lint·타입 검사 통과. 69개 테스트 파일, 2,231개 통과·1개 건너뜀                                                                   |
| `pnpm site:build` | 첫 실행은 종료 코드 0, Vite 빌드 및 33개 주소와 404 HTML 생성 기록 확인. 메타 생성 과정의 로컬 포트에 샌드박스 `EPERM` 경고 발생 |

경고 없는 사이트 빌드를 확인하기 위해 샌드박스 밖 재실행을 요청했으나 사용자가 거절해
재실행하지 않았다. 따라서 사이트 빌드가 완전히 깨끗하게 검증됐다고 기록하지 않는다.
이는 배포 화면에서 관찰한 오류와는 구분한다.

이번에는 `pnpm verify:packages`·Storybook 빌드·모든 문서의 링크·전체 접근성·외부 API를
다시 검사하지 않았다. 소비자 검증 스크립트와 CI 연결은 소스로 확인했다.
실제 신규 사용자의 작업 시간이나 이해도를 측정한 사용성 실험은 아니다.
아래 전달력 평가는 화면·동선에 근거한 검수자의 판단이다.

## 3. 유지할 강점

### UI: 반복 작업을 줄이는 기능이 이미 있다

- `TxForm.Input`은 입력·캡션·오류 표현을 묶고, 실제 SignUp 예제가 같은 소스로 표시·실행된다.
- `TxButton`은 Promise를 반환하는 작업의 로딩·비활성 상태를 처리한다.
- 확인 창·토스트는 호출 방식으로 사용하고, 테마는 CSS 토큰으로 조정한다.
- 표·달력은 서브패스와 선택 peer로 나뉘어 코어 UI 소비자에게 무조건 설치를 요구하지 않는다.

근거: [가입 폼](../../apps/site/src/pages/start/SignUp.tsx),
[버튼](../../packages/ui/src/TxButton/TxButton.tsx),
[UI 패키지](../../packages/ui/package.json).

### route-meta: 설정 한 곳에서 결과를 파생한다

- `buildRouteObjects`: 같은 트리를 React Router 설정으로 변환
- `getNavRoutes`: 숨김·사용 여부·권한 기준으로 내비게이션 데이터 생성
- `useCurrentRoute`·`useBreadcrumbs`: 현재 위치와 경로 칸 파생
- UI와 route-meta가 서로 결합되지 않아 사용자가 원하는 표현에 연결할 수 있다.

배포 데모에서 실제 확인한 결과:

| 조작      | 관찰 결과                                                        |
| --------- | ---------------------------------------------------------------- |
| 메뉴 추가 | 코드의 `reports` 항목과 GNB·사이드바의 `＋ 리포트`가 함께 추가됨 |
| 이름 변경 | `label` 변경이 GNB·사이드바·경로의 `✎ 사용자`로 함께 반영됨      |
| 뷰어 전환 | 설정 메뉴가 양쪽에서 빠지고 메뉴 필터라는 설명이 표시됨          |

이 부분은 새로 만들 필요가 없다. 변경 표식과 결과 설명도 이미 구현되어 있으므로
과거 보고서의 ‘변경 부분 강조’ 제안을 다시 미구현으로 취급하지 않는다.

근거: [공개 진입점](../../packages/route-meta/src/index.ts),
[메뉴 데모](../../apps/site/src/pages/home/RouteMenuDemo.tsx).

### 검증 기반

패키지 빌드 후 검사하고, 별도 소비자에서 배포 파일을 검사하는 CI가 구성되어 있다.
현재 문제를 ‘테스트가 없어서 신뢰할 수 없다’고 판단할 근거는 없다.
다만 자동 검사의 통과가 처음 쓰는 사람의 도입 편의성까지 증명하지는 않는다.

## 4. 개선 사항과 우선순위

이 보고서의 높음·중간·낮음은 **핵심 장점의 전달과 도입 편의성** 기준이다.
높음이 모두 기능 장애나 공개 중단 사유라는 뜻은 아니다.

### R1 · 높음 — UI의 ‘쉽게 만드는 코드’가 데모 가까이에 부족하다

**관찰:** 홈은 실제 UI와 사용한 컴포넌트 이름을 보여 준다. 하지만 홈 UI 영역에는 그것을
만드는 짧은 코드가 없다. 이름 링크는 API 목록으로 연결되고, 상세 props는 Storybook으로 이어진다.
Components 갤러리도 실물이 중심이다. 실행 가능한 폼 코드는 Getting Started에 따로 존재한다.

**영향:** 방문자는 완성된 화면을 볼 수 있지만 ‘얼마나 간단하게 구현하는가’는 여러 화면을
옮겨 다녀야 판단할 수 있다. 단순히 다양한 UI를 제공하는 것과 쉬운 조립의 차이가 덜 드러난다.

**제안:** 홈의 대표 UI 또는 대표 기능군 한두 곳에 `결과 / 구현 코드` 보기를 붙인다.
모든 카드에 코드를 추가하지 않는다. 대표 소재는 다음이 적합하다.

- 캡션·오류를 가진 `TxForm.Input`
- 비동기 핸들러만 넘기면 로딩 상태를 처리하는 `TxButton`
- `await TxDialog.confirm(...)` 또는 `TxToast.show(...)`

‘직접 해야 할 일’과 ‘컴포넌트가 맡는 일’을 한 문장으로 설명한다. 폼의 업무 검증 로직까지
자동 제공하는 것처럼 쓰지 않는다. 직접 구현한 가짜 장문 코드와 줄 수를 비교하지 않는다.
완성 파일과 발췌의 경계를 밝히고 실제 예제 소스를 재사용한다.

**완료 기준:** 대표 UI를 본 자리에서 짧은 구현을 확인·복사하고 완성 파일로 이동할 수 있다.

근거: [Home](../../apps/site/src/pages/Home.tsx),
[UI 기능군](../../apps/site/src/pages/home/UiGroups.tsx),
[컴포넌트 링크](../../apps/site/src/components/Used.tsx).

### R2 · 높음 — UI와 route를 시작하는 경로가 대등하게 드러나지 않는다

**관찰:** 홈의 큰 버튼은 `UI 둘러보기`와 공통 `시작하기`다. route는 설명 속 앵커로 연결된다.
Getting Started는 패키지 선택·저장소 빌드·UI 가입 폼을 중심으로 이어지고,
Documents는 처음부터 순서대로 읽는 동선을 권한다. route만 필요한 사람의 별도 시작점은
패키지 표·하위 가이드에서 찾아야 한다.

**제안:** 두 가지 작업을 바로 고를 수 있게 한다.

| 목적                   | 이어질 내용                                                             |
| ---------------------- | ----------------------------------------------------------------------- |
| UI로 첫 화면 만들기    | 필요한 설치·CSS → 짧은 폼 → 완성 소스                                   |
| 라우트와 메뉴 설정하기 | 필요한 설치 → 작은 RouteTree → GNB·사이드바·브레드크럼 연결 → 완성 소스 |

홈에 큰 버튼을 계속 늘리지 말고 짧은 두 경로 안내나 기존 행동의 보조 링크를 사용한다.
새 문서 사이트 체계 대신 기존 Start·Routing 가이드 안의 적절한 앵커로 연결해도 된다.

**완료 기준:** route만 필요한 방문자가 UI 폼 튜토리얼을 거치지 않고 설치와 첫 메뉴 구성에 도달한다.

근거: [홈 주요 행동](../../apps/site/src/pages/Home.tsx),
[시작하기](../../apps/site/src/pages/Start.tsx), [문서 입구](../../apps/site/src/pages/DocsHome.tsx).

### R3 · 높음 — 모바일 route 시연은 코드가 결과보다 먼저 길게 나온다

**관찰:** 390×844 화면에서 route 구역은 문서 시작으로부터 약 2,914px 아래였고,
구역 높이는 약 1,886px였다. 해당 관찰은 당시 데이터·테마·폰트·설정 상태 기준이며
다른 환경의 고정 수치가 아니다. 두 열이 한 열로 바뀌면 설명·조작부 다음에 최대 26rem 코드가,
그 뒤에 GNB·사이드바 결과가 나온다. 실제 스크린샷에서도 설정 버튼 아래에는 코드만 보였다.

**영향:** 모바일에서 설정을 바꿔도 메뉴 결과를 동시에 보기 어렵다. 핵심 장점은 구현됐지만
코드에 익숙하지 않은 첫 방문자는 효과를 보기 전에 긴 스크롤을 해야 한다.

**제안:** 모바일에서는 결과를 코드보다 먼저 놓거나 `결과 / 설정 코드` 탭을 사용한다.
홈의 UI 기능군은 모바일에서 일부 요약 후 전체 보기로 연결하는 방안도 검토한다.
데스크톱의 코드·결과 병렬 배치는 유지할 가치가 있다.

**완료 기준:** 모바일에서 메뉴 추가·이름 변경을 누른 뒤 긴 코드 블록을 지나지 않고
그 결과를 확인한다. 키보드 읽기 순서도 시각 순서와 일치시킨다.

근거: [홈 구역 순서](../../apps/site/src/pages/Home.tsx),
[코드 우선 grid](../../apps/site/src/pages/home/RouteMenuDemo.tsx).

### R4 · 중간 — route의 최소 완성 예제가 여러 곳에 나뉜다

**관찰:** 홈은 발췌라는 설명을 정확히 제공하고, 빠진 `element`·`role`·`barItem`·`sideItem`을
명시한다. 완성 구현은 Example Routes와 Example App으로 연결된다.
가이드에는 선언·라우터·메뉴·현재 위치·권한을 단계별로 다루는 코드 예제가 있다.
즉 예제가 없는 문제가 아니라 **가장 작은 실행 단위가 한눈에 모이지 않는 문제**다.

**제안:** 설치 안내를 전제로 한 최소 완성 예제 하나를 제공한다.
2~3개 화면, 트리, UI 연결, Router, CSS를 포함하며 업무 API·로그인·서버 상태 관리는 제외한다.
실제 실행 소스와 표시 코드를 같은 파일에서 가져오고, 홈은 그 예제로 직접 연결한다.
프로젝트 전체의 큰 예제와 작은 시작 예제의 역할을 구분한다.

**완료 기준:** 정의되지 않은 식별자 없이 새 앱에 적용할 수 있고, 화면 하나를 트리에 추가하면
라우터·메뉴·경로 표시가 함께 반영된다. 이 변경도 실습으로 안내한다.

### R5 · 중간 — 설치 단계의 마찰과 사용 코드의 단순함을 구분해야 한다

**관찰:** npm 미배포 상태를 정직하게 안내하고, 저장소 clone·Node 전환·빌드·pack·로컬 설치 절차를 제공한다.
하지만 ‘쉽다’는 메시지 다음에 저장소 빌드가 나오면 초심자가 패키지 사용 자체가 복잡하다고 느낄 수 있다.

**제안:** 공통 설치 준비는 한 번만 하고, UI와 route의 사용 단계는 각각 짧게 보여 준다.
수동 배포 `.tgz` 제공이나 향후 템플릿 제공은 필요가 확인될 때 별도로 검토한다.
이번 검수만을 근거로 npm 배포를 진행하거나 검증되지 않은 실행 명령을 노출하지 않는다.

**완료 기준:** 현재 가능한 설치 경로를 유지하면서 설치 준비·UI 사용·route 사용의 경계를 알 수 있다.

### R6 · 낮음 — 다섯 패키지의 안내가 일부 일치하지 않는다

**관찰:** 홈과 Start는 다섯 패키지를 설명하지만 Footer에는 fns가 빠져 있다.
홈·Documents·Tutorial의 ‘네 패키지’ 표현은 기존 네 개를 쓰는 실습 맥락일 수 있으므로
무조건 다섯으로 바꾸면 오히려 부정확해진다.

**제안:** Footer에 fns를 추가한다. 튜토리얼은 ‘UI·route-meta·hooks·axios로 목록 만들기’처럼
실제로 사용하는 패키지를 명시한다. 홈의 다섯 패키지는 유지하되 UI·route의 대표 가치가
패키지 개수 소개에 묻히지 않게 한다.

**완료 기준:** 전체 제공 목록과 특정 실습의 사용 목록을 혼동하지 않는다.

근거: [Footer](../../apps/site/src/pages/SiteFooter.tsx),
[Tutorial](../../apps/site/src/pages/Tutorial.tsx), [Documents](../../apps/site/src/pages/DocsHome.tsx).

### R7 · 후속 기술 검토 — 홈 시연이 React Router 내부 Context에 의존한다

**관찰:** `RouteMenuDemo.tsx`는 외부 사이트 주소를 바꾸지 않고 `useBreadcrumbs`를 시연하기 위해
`UNSAFE_LocationContext.Provider`를 사용한다. 이 코드는 패키지 본체가 아니라 사이트 데모에 있다.
현재 동작 결함은 확인하지 않았다.

**제안:** 즉시 공개 API를 바꾸지 않는다. Router 업데이트 시 해당 시연을 회귀 확인 항목으로 두고,
공개 API만 사용하는 격리 방식 또는 별도 예제 화면이 필요한지 검토한다.
데모 구현의 내부 우회가 사용자 설치 코드에 필수인 것처럼 노출되지 않게 유지한다.

## 5. 추천하는 홈 메시지와 동선

현재 제목은 유지해도 된다. 전면에 드러낼 두 가지 약속은 다음과 같다.

> **UI는 조립하고, 메뉴는 라우트에서 만드세요.**
>
> 폼·모달·레이아웃의 반복 작업은 컴포넌트에 맡기고,
> 라우트 트리 한 곳에서 GNB·사이드바·브레드크럼을 관리하세요.

이것은 문구 초안이며 반드시 제목을 교체하라는 뜻이 아니다.
문구보다 그 아래에서 같은 약속을 증명하는 것이 우선이다.

```text
핵심 설명
├─ UI: 작동하는 결과 ↔ 짧은 구현 코드 → UI 시작 안내
└─ Route: 작은 트리 ↔ 메뉴·경로 변화 → route 최소 완성 예제
       ↓
테마 변경 / 완성된 업무 화면 / 나머지 도구 / 설계 사례
```

현재 기능군 갤러리·토큰 체험·Example·설계 사례를 삭제할 필요는 없다.
라이브러리를 처음 평가하는 단계에는 구현 메커니즘보다 결과와 사용법을 먼저 보여 준다.
`buildRouteObjects` 등의 함수명 상세는 코드·가이드에서 설명하고 홈 문장은 짧게 유지한다.

## 6. 작업 순서와 마무리 기준

1. **UI 대표 시연 옆에 최소 코드와 첫 구현 링크 추가** — R1
2. **UI와 route의 두 시작 경로 정리** — R2·R4·R5
3. **모바일 route 결과 우선 배치** — R3
4. **패키지 목록·실습 문구 정합성 수정** — R6
5. **데모 내부 Router 의존 추적** — R7, 업데이트 시 검토

첫 네 항목을 완료하면 사이트 전달력 개선은 마무리하고 실제 소비자 프로젝트 사용에서
나오는 피드백을 받는 단계로 전환할 수 있다. 새 컴포넌트나 추상화 API를 더 늘려야 한다는 결론은 아니다.

새 사용자에게 다음 세 가지를 실제로 해 보게 하면 완료 여부를 판단하기 좋다.

- UI 폼 하나를 만들고 오류 메시지 또는 비동기 버튼을 적용한다.
- 트리에 화면 하나를 추가하고 메뉴·브레드크럼 반영을 확인한다.
- 필요한 패키지만 선택하고 스타일·Router 필수 조건을 찾는다.

걸린 시간·막힌 지점·질문을 기록한다. 측정하지 않은 ‘몇 분 완성’·‘몇 배 빠름’ 수치는 쓰지 않는다.
추가 작업의 진행 상태는 저장소 규약에 따라 `docs/README.md` 한 곳에서 관리한다.
