# 008 · 프로젝트 검수와 사이트 개선 작업안

> 2026-10-15 검수 기준. Claude가 후속 구현을 진행하기 위한 작업 명세다.
> 이 문서는 **검수 근거와 제안한 작업 범위**를 갖는다. 실제 진행 상태와 다음 할 일은
> [README](README.md) 한 곳에서 관리한다. 이 문서를 작성하면서 앱·패키지 코드는 수정하지 않았다.

## 1. 목표와 판단

사이트의 목적은 두 가지다.

1. 다음 프로젝트에서 필요한 패키지와 기능을 찾고, 설치해서 화면을 만들 수 있게 한다.
2. 포트폴리오 방문자가 해결한 문제, 설계 판단, 실제 동작, 검증 근거를 이해하게 한다.

라이브러리의 패키지 분리와 구현 기반은 충분히 갖춰져 있다. 다음 단계는 컴포넌트 수를
늘리는 일보다 **무엇을 제공하는지 보여 주고, 실제로 도입할 수 있음을 검증하는 일**이다.

특히 사용자는 현재 홈만 보고 라이브러리가 무엇인지 쉽게 이해되는지 확신하기 어렵고,
UI 소개가 부족하다고 느꼈다. **홈의 제품 설명과 UI 시연을 우선 개선한다.**

추가로 사용자가 강조한 핵심 장점은 **라우트 메타데이터를 미리 선언하면 GNB와 사이드바를
쉽게 구성할 수 있다는 것**이다. UI 실물과 함께 이 기능을 홈의 대표 가치로 노출한다.
UI를 강조하면서 route-meta를 하단 패키지 목록으로만 밀어내지 않는다.

## 2. 검수 결과와 범위

소스·문서·설정을 검토하고 아래 명령을 실행했다.

| 항목              | 결과                                                |
| ----------------- | --------------------------------------------------- |
| `pnpm check`      | lint·타입 검사 통과, 테스트 1,827개 통과·1개 건너뜀 |
| `pnpm build`      | 4개 패키지 빌드 통과                                |
| `pnpm site:build` | 통과. 큰 JS 청크와 폰트 `@import` 순서 경고 발생    |

위 수치는 검수 시점의 기록이다. 브라우저에서의 화면·모바일·접근성·실제 로딩 성능은
이번 검수에서 확인하지 않았다. 빌드 경고를 실제 사용자 체감 성능 측정 결과로 해석하지 않는다.

### 강점

- 여러 서비스에 복사하던 코드를 공통 패키지로 추출했다는 문제와 목적이 명확하다.
- UI·라우트 메타데이터·훅·HTTP의 책임이 분리되어 있다. HTTP는 React에 의존하지 않는다.
- 토큰 취득, 401 대응, 응답 형식 등 서비스 정책은 앱이 옵션으로 주입한다.
- CSS 변수와 레이어로 디자인을 바꾸고, 표·달력의 선택 의존성은 서브패스로 나눈다.
- Storybook·튜토리얼·업무 화면 예제와 회귀 테스트가 있다. 사이트 자체도 패키지를 사용한다.

### 부족한 점

- 기능과 원칙을 설명하는 글에 비해 UI의 범위와 실제 모습을 빠르게 확인하기 어렵다.
- 사이트의 소스 alias 연결은 배포 파일을 설치한 외부 소비자 검증을 대신하지 못한다.
- 배포 워크플로에 lint·타입 검사·테스트를 통과해야 하는 조건이 없다.
- Profile이 비어 있고, 설계·개선 기록이 포트폴리오용 사례로 연결되지 않았다.
- 단위 테스트 외에 실제 브라우저 동작과 배포 패키지에 대한 검증을 보강해야 한다.

## 3. 홈 진단: UI 개수보다 보여 주는 순서의 문제

현재 `apps/site/src/pages/Home.tsx`에는 UI 설명이 없는 것은 아니다.
`49 components`, 폼 데모, 테마 코드, 패키지 설명이 이미 있다. 다만 다음 문제가 있다.

- 첫 화면의 주제는 React 라이브러리이고 설명은 검색·목록·폼·HTTP까지 넓다.
  방문자가 구체적인 UI 결과물을 보기 전에 여러 개념을 읽어야 한다.
- `Why txstack`과 원칙이 실물 데모보다 먼저 나온다. 제품 이해보다 배경 설명이 앞선다.
- 폼 하나만으로는 표·레이아웃·다이얼로그·피드백까지 제공하는 UI의 범위를 알기 어렵다.
- `49`라는 숫자는 실제 공개 컴포넌트·내부 부품·파생 컴포넌트의 계산 기준을 설명하지 못한다.
  숫자를 강조하기 전에 기능군과 실물을 보여 줄 필요가 있다.
- 홈의 코드에는 `submit`, `errors` 정의가 생략되어 있고 실제 데모 구현과 다르다.
  복사해 실행할 코드와 설명용 발췌를 구분해야 한다.
- npm 배포 전이라는 안내는 있지만 홈의 복사 가능한 설치 명령은 배포 후 기준이다.
  처음 방문한 사람이 복사 버튼부터 누르면 현재 도입 경로와 어긋난다.

따라서 **제공하는 UI → 실제로 만드는 화면 → 함께 쓰는 도구 → 설계 배경** 순서로 바꾼다.
아래 문구와 배치는 구현 기준안이며, 실제 화면에서 길이와 밀도를 확인해 다듬는다.

## 4. 홈 개편 명세 — 최우선

### 4.1 첫 화면: 대상·구성·결과를 한 번에

추천 제목:

> 검색·목록·입력 폼을 만드는 React UI 라이브러리

추천 설명:

> txstack은 관리 화면과 업무용 서비스에 필요한 버튼, 입력 폼, 데이터 표, 모달,
> 메뉴와 레이아웃을 제공합니다. CSS 변수로 디자인을 바꾸고, 필요한 경우 라우팅·URL 상태·
> HTTP 도구를 함께 사용해 화면을 완성할 수 있습니다.

첫 화면의 설명 또는 데모 캡션에 다음 강점도 짧게 노출한다.

> 라우트 메타데이터를 한 번 정의하고, GNB와 사이드바를 같은 설정으로 구성하세요.

이어서 짧은 보조 설명:

> UI만 사용하거나, 필요한 패키지를 골라 조합할 수 있습니다.

주요 행동은 `UI 둘러보기`(`/docs/components`)와 `시작하기`(`/docs/start`) 두 개로 둔다.
실제 업무 예제는 시연 영역 가까이에 별도 링크로 제공한다. 첫 화면의 주요 버튼을 늘리지 않는다.

첫 화면에는 긴 코드 대신 작은 실제 UI 미리보기를 함께 배치한다. 넓은 화면은 설명과 데모를
나란히, 좁은 화면은 제목·설명·행동 다음에 데모가 나오게 한다.

### 4.2 UI 미리보기: 화면이 제품 설명이 되게

대표 미리보기는 **회원 또는 팀 관리 화면의 작은 일부**로 구성한다.

- 검색 입력과 상태 필터
- 작은 목록과 상태 배지
- 편집 버튼 → 모달 또는 슬라이드 패널
- 입력 폼 → 저장 → 성공 토스트
- 로딩·빈 결과·오류는 선택적으로 확인할 수 있는 간단한 상태 시연

홈에서는 로컬 샘플 데이터로 재현 가능하게 만들고 실제 저장처럼 오해하지 않도록
`샘플 데이터로 동작하는 데모`를 짧게 표시한다. 외부 API 상태 때문에 첫인상이 달라지지 않게 한다.
정교한 전체 CRUD 앱은 기존 Example을 재사용하고 홈 데모의 범위를 작게 유지한다.

AG Grid를 홈에서 바로 로드할지는 번들 영향을 확인하고 결정한다. 가벼운 미리보기를 위해
새로운 공개 표 컴포넌트를 만들지 않는다. 무거운 시연은 사용자 동작 후 로드하거나 Example으로 연결한다.

데모 아래에는 실제로 사용한 컴포넌트 이름을 링크로 표시한다. 화면 장식·가짜 탭·반응 없는 버튼은 두지 않는다.

### 4.3 UI 제공 범위: 기능군으로 보여 주기

| 기능군        | 대표 컴포넌트                                | 방문자가 이해할 결과                   |
| ------------- | -------------------------------------------- | -------------------------------------- |
| 입력과 폼     | TxInput, TxForm, TxDropdown, TxCheckBox      | 입력·선택·검증 메시지를 갖춘 폼        |
| 데이터와 목록 | TxAgGrid, TxPagination, TxBadge              | 정렬·페이지 이동·상태 표시가 있는 목록 |
| 창과 피드백   | TxModal, TxSlidePanel, TxDialog, TxToast     | 편집·확인·처리 결과 안내               |
| 화면 구조     | TxAppShell, TxNavBar, TxSideNav, TxTabs      | 헤더·메뉴·본문을 갖춘 업무 화면        |
| 상태 표시     | TxLoading, TxSkeleton, TxEmptyState, TxAlert | 대기·빈 결과·오류를 설명하는 화면      |

텍스트 카드만 반복하지 말고 기능군마다 작은 실물 또는 대표 미리보기를 곁들인다.
전체 목록은 기존 Components 갤러리로 연결한다. 개별 props와 모든 변형은 Storybook이 계속 소유한다.
공개 API·파생 컴포넌트·내부 부품을 구분해 개수 표기를 확인한다. 확인 전에는 숫자를 새로 단정하지 않는다.

### 4.4 디자인 변경도 결과로 보여 주기

CSS 변수 코드만 제시하지 말고 같은 작은 UI의 강조색·모서리·라이트/다크 변화를 직접 비교하게 한다.
예제는 실제 `--tx-*` 토큰으로 구현하고 변경한 토큰과 짧은 코드를 함께 보여 준다.
체험 상태가 사이트 전체 설정을 의도치 않게 바꾸지 않도록 범위를 정한다.
다크 모드가 루트 클래스 등에 의존한다면 먼저 기존 CSS 동작을 확인한다.

### 4.5 대표 기능: 라우트 설정 하나로 GNB와 사이드바 구성

이 기능은 패키지 소개 카드 한 장으로 끝내지 않고 **홈 상단부의 독립 시연 섹션**으로 둔다.
UI 제공 범위 다음에 배치해 “화면 부품이 있다”에서 “화면 구조도 쉽게 조립한다”로 이어지게 한다.

추천 제목:

> 라우트 한 곳에 정의하고, GNB와 사이드바를 함께 구성하세요

추천 설명:

> 경로와 메뉴 이름, 하위 메뉴를 메타데이터 트리로 선언합니다. 같은 트리에서 라우터와
> 메뉴 데이터를 만들고, UI 컴포넌트에 연결해 상단 메뉴와 사이드바를 구성합니다.
> 메뉴를 추가하거나 이름을 바꿀 때 같은 설정에서 관리할 수 있습니다.

시연 구성:

- 왼쪽에는 대시보드·회원·설정 등 작은 라우트 트리의 실제 코드를 보여 준다.
- 오른쪽에는 그 트리를 사용하는 GNB·사이드바·현재 화면을 함께 보여 준다.
- 메뉴를 누르면 화면과 선택 상태가 일치하게 바뀌고, 하위 메뉴의 계층도 확인할 수 있게 한다.
- 메뉴 추가 또는 이름 변경을 선택하면 코드와 GNB·사이드바가 같은 트리에서 함께 바뀐다.
  자유 코드 편집기 대신 미리 준비한 설정 전환으로도 충분하다.
- 권한 필터 체험은 선택적으로 제공한다. 메뉴 노출 필터이며 접근 제어 전체를 제공한다고 표현하지 않는다.
- `이 사이트의 메뉴도 같은 방식으로 구성했습니다`라는 설명과 기존 Routing 가이드·Example의
  해당 화면으로 이동하는 링크를 제공한다. 구현 시 실제 연결된 경로를 확인한다.

구현의 역할을 정확하게 보여 준다.

`RouteTree → buildRouteObjects → 라우터`,
`같은 RouteTree → getNavigableRoutes → TxNavBar / TxSideNav`

route-meta는 라우트 변환과 메뉴 데이터를 제공하고, 화면 표현은 UI 컴포넌트와 소비자 앱의
연결 코드가 담당한다. 메타데이터만 선언하면 연결 코드 없이 메뉴 UI까지 자동 생성되는 것처럼
표현하지 않는다. 트리 정의뿐 아니라 메뉴 데이터를 UI로 연결하는 짧은 코드도 함께 제공한다.
별도 메뉴 배열을 복사해 두고 시연하지 말고, 코드와 화면이 실제로 같은 설정을 사용하게 한다.

중첩 라우터가 필요하면 기존 Example의 격리 방식을 먼저 확인한다. 홈 데모 조작이 사이트의
전체 메뉴·주소를 의도치 않게 바꾸지 않도록 한다. 새 공개 API를 만들지 않고 기존 기능으로 구성한다.

### 4.6 네 패키지의 관계와 설치

UI를 소개한 다음 아래 관계를 짧게 설명한다.

| 패키지                | 필요한 때                                              |
| --------------------- | ------------------------------------------------------ |
| `@txstack/ui`         | 버튼·폼·표·메뉴 등 화면 부품이 필요할 때               |
| `@txstack/route-meta` | 라우트 정의로 메뉴와 현재 위치를 함께 관리할 때        |
| `@txstack/hooks`      | 객체 상태 또는 URL 검색 조건을 관리할 때               |
| `@txstack/axios`      | 인증·응답·오류 처리 정책을 HTTP 클라이언트에 연결할 때 |

모든 패키지를 설치해야 한다고 읽히지 않게 한다. 표·달력의 추가 의존성은 관련 안내에 명시한다.
권한별 **메뉴 필터링**과 실제 페이지 접근 제어·서버 권한 검증은 구분한다.

npm 배포 전에는 현재 가능한 설치 안내로 연결하는 행동을 우선한다.
배포 후 명령을 남긴다면 복사 영역 자체에 조건을 표시한다. 배포 상태는 기존
`PrePublish.tsx`의 관리 방식을 재사용하고 여러 파일에 별도 플래그를 만들지 않는다.

### 4.7 권장 최종 순서

1. 한 문장 소개 + 대표 UI 데모 + 주요 행동
2. 기능군별 UI 제공 범위
3. 라우트 설정 하나로 GNB·사이드바 구성 시연
4. 토큰 변경과 다크 모드 체험
5. 네 패키지의 역할과 선택 사용 안내
6. 완성된 업무 화면 예제와 시작하기 연결
7. 만든 배경·설계 원칙·프로젝트 사례 연결

기존 `STORY`, `PRINCIPLES`, `FEATURES`, 패키지 카드의 반복 설명은 합친다.
읽을 분량을 늘리는 대신 실물을 앞당긴다. 복사 가능한 코드는 실행 가능하게 제공하거나
생략한 부분을 명시하고 완성 소스로 연결한다.

### 홈 완료 기준

- 처음 온 사람이 첫 화면에서 React UI 라이브러리라는 점과 주 사용 대상을 알 수 있다.
- 긴 배경 글을 읽기 전에 최소 폼·목록·창 등 서로 다른 UI 기능을 볼 수 있다.
- 첫 화면에서 route-meta의 메뉴 구성 강점을 알 수 있고, 상단부 시연에서 같은 트리로
  GNB와 사이드바가 구성·변경되는 것을 확인할 수 있다.
- route-meta의 데이터 생성과 UI 연결 역할이 구분되고, 라우트·메뉴를 별도로 중복 선언하지 않는다.
- UI만 사용할 수 있고 나머지 패키지는 필요에 따라 고른다는 점이 드러난다.
- `UI 둘러보기 → Components → API/Storybook`, `시작하기 → 설치 → 첫 화면` 동선이 이어진다.
- 데모의 모든 행동이 실제 동작하며 입력에 보이는 label과 키보드 접근이 있다.
- 모바일에서 페이지 전체 가로 넘침이 없고, 표·코드의 넘침은 해당 영역 안에서 처리한다.
- 홈을 열자마자 불필요한 AG Grid·외부 요청이 실행되지 않는지 확인한다.
- 라이트·다크, 키보드, 작은 화면과 넓은 화면을 실제 브라우저에서 확인한다.
- 사용자에게 첫 화면만 보여 준 뒤 “무엇을 제공하고 어디서 시작하는가”를 확인받는다.

## 5. 후속 작업: 안정성과 도입 검증

### A. HTTP 로그의 마스킹 보완

근거: `packages/axios/src/interceptors.ts`의 `consoleErrorLogger`는
`error.response.data`를 마스킹 없이 문자열로 출력한다. `shortUrl`은 쿼리를 그대로 포함하고,
기존 `maskSensitive`는 최상위 객체 필드만 처리한다.

- 오류 응답과 URL 쿼리에 민감 값이 남는 조건을 회귀 테스트로 재현한다.
- 성공·실패 로그와 사용자 제공 로깅 훅에 전달되는 데이터의 마스킹 범위를 정리한다.
- 중첩 객체·배열·문자열 본문에 대해 지원하는 범위와 제한을 문서화한다.
- 원본 요청·응답 데이터는 변경하지 않는다. 공개 옵션을 바꾼다면 예제 코드로 먼저 합의한다.

완료 기준: 테스트에 심은 민감 값이 의도한 모든 로그 경로에서 사라지고 기존 인증·오류 동작이 유지된다.

### B. 배포 파일을 설치하는 검증

근거: `apps/site/vite.config.ts`는 대부분의 패키지 import를 소스 파일로 연결한다.

- 패키지를 빌드하고 `pnpm pack`으로 만든 `.tgz`를 별도 임시 소비자에 설치한다.
- 최소 소비자가 UI의 JS·타입·CSS를 정상적으로 사용하는지 확인한다.
- AG Grid·달력을 설치하지 않은 코어 소비자와 각 서브패스를 쓰는 소비자를 구분해 확인한다.
- hooks의 각 진입점, route-meta, React 없는 Node의 axios 사용을 확인한다.
- 지원을 선언한 React 버전 범위에 대한 검증 범위와 미검증 범위를 기록한다.

기존 실제 서비스에 적용하는 작업은 [006_adoption](006_adoption.md)에 따라 사용자가 진행한다.
자동화용 최소 소비자 검증과 실제 서비스 화면 이관을 혼동하지 않는다.

### C. CI와 배포 조건

근거: `.github/workflows/pages.yml`은 설치 후 사이트·Storybook 빌드를 실행하며 `pnpm check`는 실행하지 않는다.

- PR에서 lint·타입·테스트·패키지 빌드가 실행되게 한다.
- 타입 검사가 dist를 참조하는 곳이 있으므로 패키지 빌드 후 검사 순서를 확인한다.
  빌드가 dist를 정리하는 동안 타입 검사가 동시에 읽지 않도록 한다.
- main의 배포도 품질 검사가 실패하면 진행되지 않게 한다.
- 필요하면 B의 최소 소비자 검증을 재사용한다. npm publish를 추가하지 않는다.

### D. 사이트 번들·폰트·브라우저 검증

검수 빌드에서 주요 JS 청크 약 787KB(gzip 248KB), AG Grid 관련 청크 약 1,064KB(gzip 300KB)가 관찰됐다.
초기 전송량은 Network에서 별도로 확인해야 한다.

- `routes.tsx`의 정적 import와 `searchIndex.ts`의 동적 import 중복 경고를 점검한다.
- 페이지 지연 로딩 시 검색 색인·목차·스크롤 이동 동작이 유지되는지 확인한다.
- `theme.css`의 외부 폰트 import 순서 경고를 해결하고 실제 적용 여부를 확인한다.
- Pages 하위 경로에서 새로고침·직접 링크·앵커·Storybook 이동을 확인한다.
- 현재 404.html 폴백은 화면 복원과 HTTP 상태 코드를 구분해 평가한다.
  필요하면 주요 소개 페이지의 사전 렌더링과 공유 메타데이터를 별도 작업으로 검토한다.
- 변경 전후의 초기 다운로드·청크·브라우저 결과를 기록한다. 경고 한도만 올려 숨기지 않는다.

## 6. 문서 사이트와 포트폴리오 콘텐츠

기존 Documents·API·Example 구조는 유지하고 목적별 진입점을 보강한다.

| 자리                  | 책임                                         |
| --------------------- | -------------------------------------------- |
| Home                  | 무엇인지 이해하고 UI 실물과 다음 행동을 찾기 |
| Getting Started       | 현재 가능한 설치 방법부터 첫 화면 실행까지   |
| Components            | 기능군별 UI 갤러리와 레퍼런스 연결           |
| Guide / Tutorial      | 실제 작업 순서와 여러 패키지의 조합          |
| API / Storybook       | 정확한 공개 API와 개별 부품의 변형           |
| Example               | 검색·편집·저장·실패까지 연결된 업무 화면     |
| About / 프로젝트 사례 | 문제·설계·검증·한계·만든 사람 소개           |

### 도입 안내

- 필요한 기능별 패키지 선택과 추가 의존성을 안내한다.
- 설치 → CSS → 파일 작성 → 실행 결과 → 문제 해결을 한 동선으로 연결한다.
- 복사 가능한 코드는 완성 파일과 일치하게 유지한다. 기존 raw source 사용 방식을 우선 재사용한다.
- 공개 패키지 상태와 예제의 mock/실제 API 여부를 명확히 한다.

### 프로젝트 사례

[007_about_draft](007_about_draft.md)를 재사용해 아래 흐름으로 구성한다.

1. 여러 서비스의 중복 UI·HTTP 코드라는 문제
2. 네 패키지의 경계와 앱에 남겨 둔 정책
3. 주요 설계 판단: CSS 토큰, 선택 의존성, 라우트 단일 정의, URL 상태
4. 실제로 발견하고 고친 결함 2~3건의 원인·해결·검증
5. 동작 데모·소스·테스트 근거
6. 현재 제약과 다음 검증 단계

성과는 컴포넌트 개수만으로 설명하지 않는다. 개발 시간 절감·코드 감소·도입 서비스 수는
측정하거나 사용자에게 확인한 사실만 싣는다. 소비자 프로젝트 이름 공개는 기존 문서 원칙을 따른다.

Profile에는 이름·역할·소개·링크가 필요하다. 사용자의 경력·개인 연락처·성과를 임의로 채우지 않는다.
Contact의 GitHub 이슈 안내는 유지하되 협업 연락 창구는 사용자 제공 정보가 있을 때 추가한다.

## 7. Claude 구현 순서와 작업 경계

1. **홈 개선을 먼저 진행한다.** 기존 컴포넌트·갤러리·Example을 확인해 작은 재사용 단위로 구성한다.
2. 홈의 문구·시연·모바일·키보드 동작을 확인하고 사용자에게 결과를 보여 준다.
3. HTTP 로그 수정, 배포 파일 검증, CI를 각각 독립 작업으로 진행한다.
4. 설치 안내와 통합 예제를 정리한다.
5. 프로젝트 사례와 사용자 제공 Profile을 반영한다.
6. 성능·딥링크·공유 정보·반응형을 검증하고 결과를 기록한다.

구현 전 `CLAUDE.md`, `docs/README.md`, `docs/005_site.md`를 읽는다.
이 문서는 홈 개선의 구체적인 작업 기준을 제공하며, 새로운 공개 API·대규모 메뉴 변경까지
일괄 승인하는 문서는 아니다. 기존 공개 API와 디자인 토큰을 우선 사용한다.
API 변경이 필요하면 기존 규약대로 사용 예제로 합의한다.

소비자 서비스 이관·npm 배포·커밋·푸시는 이 작업에 포함하지 않는다.
단순 문구·배치 변경에 구현을 그대로 따라가는 테스트를 추가하지 않는다.
동작 결함에는 의미 있는 회귀 테스트를 추가하고 `pnpm build`, `pnpm check`, `pnpm site:build`를 확인한다.
시각적인 변경은 빌드 성공으로 끝내지 않고 실제 브라우저에서 검증한다.
