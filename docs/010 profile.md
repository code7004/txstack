```text

├─ Profile        소개·핵심 역량·대표 프로젝트·경력 요약
```

홈은 라이브러리 소개를 유지하고, About을 통해 작성자의 경험으로 이어지게 한다.

>
> 제품의 목적과 사용자 요구를 이해하고, 문제를 분석해 구조를 설계합니다. 관리자 시스템과
> 데이터 분석 플랫폼을 개발하며 화면, API, 데이터, 배포와 운영을 함께 다뤄 왔습니다.
> 분석과 설계가 실제 구현과 운영으로 이어지도록 제품을 완성하고, 그 과정에서 반복되는
> 기능과 설정을 재사용 가능한 구조로 정리하고 있습니다. txstack은 그 경험에서 출발한 라이브러리입니다.

중심 문구는 2026-10-16 사용자 요청에 따라 제품 이해·분석·설계·운영 가능한 제품 완성으로 수정했다.
이름·소개·역할의 나머지 표현은 공개용 초안이며, 구현 전 사용자에게 최종 표현을 확인한다.
첫 영역에는 GitHub와 대표 프로젝트 이동을 제공하고, 연락 경로는 사용자가 선택한 정보만 표시한다.
사진은 필수가 아니다. 제공된 사진이 없다면 기존 TxAvatar의 이니셜 방식을 사용한다.

이전 프로젝트들은 txstack의 UI와 hooks를 소스 폴더(`src/@core/`)에 포함해 실제로 썼다(2026-10-15 사용자 확인).
공개 문구는 그 범위로 쓰고, route-meta·axios나 npm 패키지 설치까지 썼다고 쓰지 않는다.

의료·재활 경험은 품질 기준의 배경으로 강조하고, BIM·게임·모바일·실시간 서비스 경험은
경력 타임라인에서 요약한다. 모든 프로젝트를 동일한 비중으로 펼치지 않는다.

### 4.4 경험이 txstack으로 이어지는 과정

> 여러 관리 화면을 개발하면서 같은 폼과 목록, 라우트와 메뉴 설정을 반복해서 만들었습니다.
> 이를 프로젝트마다 복사하는 대신, 서비스 정책과 공통 기능을 분리해 재사용할 수 있는
> 패키지로 정리하고 있습니다.

| 반복되던 문제                      | 현재 보여 줄 결과                            |
| ---------------------------------- | -------------------------------------------- |
| 라우트와 메뉴 정의를 따로 관리     | route-meta의 같은 트리에서 GNB·사이드바 구성 |
| 입력·목록·피드백 UI를 반복 작성    | UI 갤러리와 업무 화면 예제                   |
| 서비스마다 다른 인증·응답 처리     | axios의 정책 주입 가이드                     |
| 저장소 안에서만 동작하는 공통 코드 | `.tgz`를 별도 소비자에 설치하는 검증         |

읽은 설명을 실제 데모·가이드·소스로 확인할 수 있게 한다.

### 4.6 개발·협업 방식

공개용 문구 초안:

- 사용자가 보는 화면과 데이터가 처리되는 흐름을 함께 살펴봅니다.
- 반복되는 문제는 공통 구조로 정리하고, 서비스별 정책은 분리합니다.
- 정상 동작뿐 아니라 실패·재시도·복구와 운영 이력을 고려합니다.
- 설계 이유와 검증 결과를 남겨 다음 변경을 판단할 근거를 만듭니다.

리더십을 강조할 경우 실제 팀 규모·의사결정·협업 사례를 사용자에게 확인해 추가한다.
직함만으로 조직 운영 성과를 추정하지 않는다. AI 도구 사용 경험도 실제 활용·검증 방식이
설명될 때만 선택적으로 다룬다.

### 4.7 기술 역량

한꺼번에 수십 개의 태그를 늘어놓기보다 맥락별로 묶는다.

- **현재 주요 영역:** React·TypeScript·UI 구조·라우트와 URL 상태
- **서버·데이터·운영:** Node.js·관계형 DB·Elasticsearch·배포 흐름
- **확장 경험:** Vue·React Native·Unity/C#·Web/3D

기술별 숙련도를 백분율이나 임의의 점수로 표시하지 않는다.
최근 사용 여부와 전문성을 동일하게 취급하지 않고 프로젝트 사례로 뒷받침한다.

## 5. 프로젝트 상세 페이지 공통 형식

각 사례는 다음 순서로 작성한다.

1. **요약:** 대상 사용자·문제·기간·팀과 본인의 역할
2. **문제:** 기존 구조에서 어떤 불편과 제약이 있었는가
3. **선택:** 무엇을 나누고 어떤 대안을 고려했는가
4. **구현:** 핵심 흐름과 본인이 맡은 부분
5. **결과·검증:** 확인 가능한 동작·측정·테스트·운영 결과
6. **한계:** 남은 검증과 다시 한다면 바꿀 부분

txstack의 대표 상세 사례는 route-meta로 시작할 수 있다.

> 라우트·메뉴를 별도로 수정하던 문제 → 메타데이터 트리 → 라우터 변환·메뉴 데이터 생성 →
> GNB·사이드바·현재 위치 연결 → 실제 사이트와 데모로 확인

트리 설정만으로 UI와 접근 제어 전체가 자동 완성된다고 표현하지 않는다.
route-meta가 제공하는 데이터·변환과 소비자 앱의 UI 연결 책임을 구분한다.

프로젝트 수치와 회사명 공개 확인 전에도 익명화한 설명과 txstack 자체 사례는 작성할 수 있다.

## 7. 구현 방식

현재 `apps/site/src/pages/Profile.tsx`는 소개·기술·링크 배열을 렌더링하는 기본 틀이다.
이 계획의 역량·프로젝트·경력 목록을 표현할 수 있도록 데이터 구조와 화면을 확장한다.

- 공개용 Profile 데이터를 별도 모듈로 두고 소개·역량·프로젝트·경력·링크를 구조화한다.
- 프로젝트 상세가 생기면 요약 카드와 상세 메타데이터의 중복을 줄인다.
- 기존 TxAvatar·TxCard·TxTag 등 UI와 사이트의 Page·Block·LinkCard를 우선 사용한다.
- 현재 디자인 토큰과 반응형 규칙을 유지하고 Profile 때문에 새 스타일 체계를 만들지 않는다.
- 긴 경력은 모바일에서 읽는 순서대로 배치하며 가로 타임라인을 강제하지 않는다.
- 문구를 보려고 탭을 여러 번 눌러야 하는 구성보다 핵심 정보를 바로 읽는 구성을 우선한다.
- 사진·성과 그래프·이미지로 채우기 전에 내용과 증거 연결을 완성한다.
- 공개용 데이터에 원본 개인 문서 경로나 비공개 내용을 넣지 않는다.

새 경로를 추가하면 라우트 메타데이터·검색·이전/다음 이동·제목·직접 링크를 함께 확인한다.
009의 사전 렌더링·공유 정보 작업과 중복 구현하지 않고 적용 범위를 맞춘다.

## 8. 구현 순서

1. 원본과 저장소 근거로 **공개용 콘텐츠 초안**을 작성하고 확인이 필요한 항목을 표시한다.
2. 이름·소개·역할·경력·공개 연락 경로를 사용자와 확정한다.
3. Profile 한 페이지에 소개·역량·대표 프로젝트·txstack 연결·경력 요약을 구현한다.
4. 실제 소스·데모로 확인 가능한 txstack 상세 사례를 먼저 완성한다.
5. 공개 가능한 자료와 본인 역할이 확인된 과거 프로젝트 상세를 추가한다.
6. About·홈·Contact에서 연결하고 작은 화면·넓은 화면·키보드·직접 링크를 확인한다.

사용자 확인이 필요한 개인정보·경력은 임의 확정하지 않는다. 확인을 기다리는 동안
기존 UI로 레이아웃을 만들고 저장소 근거로 작성 가능한 프로젝트 콘텐츠를 진행할 수 있다.

## 9. 완료 기준과 범위

- 첫 소개에서 어떤 개발자인지, txstack과 경험이 어떻게 연결되는지 알 수 있다.
- 핵심 역량이 구체적인 프로젝트와 동작 예제로 뒷받침된다.
- 대표 프로젝트마다 본인의 역할과 팀·제품 전체의 결과가 구분된다.
- 경력과 성과 표현에 사용자 확인이 반영되고 미확인 수치가 없다.
- Profile은 요약으로 읽히며 상세 사례로 자연스럽게 이어진다.
- 모든 표시 링크가 실제 존재하고 준비 중 버튼이나 빈 페이지를 만들지 않는다.
- 라이트·다크·모바일·키보드에서 내용과 링크를 사용할 수 있다.
- 새 경로를 추가했다면 사이트 검색·메뉴·앵커·직접 링크를 확인한다.
- 문구·배치에 구현을 복제하는 테스트를 추가하지 않는다. 코드 변경에 맞는 타입·빌드 검사를 수행한다.
- `CLAUDE.md`와 문서 규약을 따르고 기존 사용자 변경사항을 보존한다.
- npm 배포·커밋·푸시·원본 개인 문서 수정은 이 계획의 범위에 포함하지 않는다.
