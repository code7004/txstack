## 개발 목적

날짜 하나와 기간을 고른다. **무거운 선택적 의존을 서브패스로 가르는 방식이 실제로 도는지 검증하는 첫 케이스**이기도 하다 — 루트 배럴을 import 한 소비자는 `react-day-picker` 를 설치하지 않아도 된다.

## 기능

```tsx
import { TxDayPicker } from "@txstack/ui/daypicker";

<TxDayPicker value={date} onChange={setDate} />;
```

`value` 를 주면 controlled 다. 고른 날짜는 **그날 00:00** 으로 맞춰서 준다.

달력은 **고른 날의 달**로 열린다. 아직 고른 것이 없으면 이번 달이다.
열어 둔 채 밖에서 값을 바꿔도 그 날이 안 보이는 달이면 **그 달로 따라간다.**

달력은 화면 맨 위 층으로 뜬다 — `overflow: hidden` 안에 넣어도 잘리지 않고,
아래가 좁으면 위로 뒤집고, **스크롤해도 따라간다.**

기간을 고르려면 `TxDayPickerRange` 를 쓴다.

## 정한 것 · 고친 것

빌드 산출물에서 잰 값이다.

| 진입점                    | 외부 의존                                           |
| ------------------------- | --------------------------------------------------- |
| `dist/index.js` (32KB)    | `react` · `react-dom` — **`react-day-picker` 없음** |
| `dist/daypicker.js` (9KB) | `react-day-picker`                                  |

루트 배럴을 import 한 소비자는 `react-day-picker` 를 설치하지 않아도 된다. `index.test.ts` 가
"서브패스 전용 컴포넌트가 루트 배럴에 없다" 로 이 경계를 지킨다.

**`react-day-picker` 의 `dist/style.css` 를 쓰지 않는다.** 그쪽 클래스 이름을 우리 것으로
갈아끼우고 레이아웃까지 직접 그렸다 — `styles.css` 에 `tx-daypicker` 69곳, `rdp-` 0곳이다.
그래서 소비자는 여전히 `@txstack/ui/styles.css` 하나만 import 하면 되고, 번들러가
`node_modules` 안의 CSS 를 처리할 수 있어야 할 이유도 없다.

`dayjs` optional peer 를 걷어냈다. 쓰던 것이 포맷·하루 경계·일수 차이 셋뿐이라 직접 쓴다.
일수 차이를 밀리초로 나누지 않는 것이 중요하다 — 서머타임이 있는 지역에서 하루가 23시간이 되면
결과가 어긋난다.

원본이 고쳐진 것들:

- **팝업을 두 컴포넌트가 각자 다시 만들었다.** 게다가 **위치를 바꾸기 전에 잰 값으로 판정**해서
  첫 열림은 늘 한 프레임 뒤처졌고, **스크롤하면 닫아 버렸다.** `TxPopup` 으로 갈아끼웠다
- **라이브러리가 `alert()` 를 띄웠다.** 이제 `maxDays` 를 넘는 날은 아예 눌리지 않는다 —
  고르고 나서 알리는 것보다 못 고르게 하는 편이 낫다
- `TxInputLike` 를 쓰면서 열림 상태를 안 넘겨 스크린리더가 늘 "닫힘" 으로 들었다
- `header` render prop 이 값과 콜백 넷을 되넘기는 복잡한 시그니처였다 → `ReactNode` + `ref`
- **좌우 버튼이 보이는데 눌리지 않았다.** `react-day-picker` 10 은 그 버튼들을 **달 캡션 안이
  아니라 달들(`__months`) 옆에 한 벌만** 놓는데, CSS 는 캡션 안에 있다고 보고 캡션에
  `position: relative` 를 줘 기준을 세웠다. 그래서 (1) 버튼의 기준이 캡션이 아니라 **팝업**이
  되어 헤더가 있으면 엉뚱한 줄에 얹혔고, (2) **캡션이 버튼보다 뒤에 그려져 통째로 덮었다** —
  클릭이 전부 캡션에 먹혔다. 기준을 `__months` 로 옮기고 캡션에서 `position` 을 걷어냈다.
  띠의 빈 가운데가 달 이름을 덮지 않게 띠는 `pointer-events: none`, 버튼만 `auto` 다.
  **jsdom 에는 배치가 없어 렌더로는 안 보인다** — CSS 를 글자로 읽는 계약 테스트가 이걸 지킨다
- **밖에서 넣은 값을 달력이 따라가지 않았다.** `header` 의 프리셋 버튼("최근 90일")으로
  기간을 넣으면 값은 들어가는데 화면은 보던 달에 그대로 있어 **고른 것이 안 보였다.**
  펴 놓을 달을 `defaultMonth`(처음 한 번)에서 **`month` 로 바꿔 우리가 쥔다**(`useVisibleMonth`).
  규칙은 둘이다 — **열 때는 값의 달로 맞추고**, 열린 채 들어온 값이 **안 보이는 달이면 옮긴다.**
  이미 보이는 달이면 옮기지 않는다: 두 달을 펴 놓고 오른쪽 달에서 시작일을 고를 때 화면이
  옆으로 밀리면 고르던 자리가 사라진다. `ref` 로 넣든 `value` 로 넣든 같은 길이다
- **달력이 고른 날의 달이 아니라 늘 오늘 달로 열렸다.** 8월 15일을 들고 열어도 9월이 펼쳐져
  20일을 누르면 9월 20일이 들어왔다. 원본도 같았다 — `TxDayPickerRange` 만 `defaultMonth` 를
  줬고 `TxDayPicker` 는 빠져 있었다. **테스트가 오늘 달에 기대 있어 8월 동안은 우연히
  통과하다가 9월로 넘어오며 빨개졌고, 그때 드러났다.** 이제 달을 로케일 없이 `data-day` 로
  읽어 "고른 날의 달로 연다" 를 단독으로 검사한다

### 포털된 팝업은 앵커의 토큰을 못 읽는다

`TxDayPicker` 의 달력이 **칸 폭 0 으로 그려지는 것**을 Storybook 실측에서 발견했다.

토큰을 앵커(`.tx-daypicker`)에 선언했는데 달력은 `document.body` 로 포털된다. CSS 변수는
DOM 을 따라 상속되므로 **앵커의 선언이 팝업에 닿지 않는다.** 값이 통째로 사라져 칸 폭이 0 이 되고
색이 안 칠해진다.

**`TxDropdown` 과 `TxCombobox` 도 같은 상태였다** — 목록 항목의 여백·글자크기·짚은 줄 배경이
전부 안 먹고 있었다. 셋 다 팝업 쪽 클래스(`.tx-daypicker__panel` · `.tx-dropdown__list` ·
`.tx-combobox__list`)로 토큰 선언을 옮겼다.

**규칙:** 팝업 안에서 쓰는 토큰은 팝업 쪽에 선언한다. 전역 토큰(`--tx-color-*`)은 `:root` 에
있어 어디서든 닿는다. 세 컴포넌트의 CSS 계약 테스트가 이걸 지킨다 — 앵커에만 선언된 토큰을
팝업 쪽 규칙이 쓰면 실패한다.
