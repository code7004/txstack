# 900 · 공통 규약

**컴포넌트 하나에 속하지 않는 것들.** 커스터마이징 방식 · 이식 규칙 · 닫아 둔 결정.
컴포넌트별 문서는 [000_README](000_README.md) 의 목록에서 찾는다.

## 커스터마이징 방식 — 결정됨

**CSS 커스텀 프로퍼티 토큰(`--tx-*`) + `tx` 캐스케이드 레이어.** `legacy` 에서 이미 결론이 났고
`TxSpinner` · `TxButton` · `TxLoading` · `TxFlex` 4개가 이 방식으로 이행됐다. **다시 논의하지 않는다.**

### 1. 토큰이 커스터마이징의 정문이다

소비자는 `tokens.css` 의 전역 토큰만 덮으면 된다.

```css
:root {
  --tx-color-primary: #7c3aed;
  --tx-radius: 9999px;
}
```

컴포넌트 토큰(`--tx-button-bg` 등)이 이 값을 **기본값으로 받는다.** 그래서 한 줄만 바꾸면
`hover` · `focus` · `.dark` 가 저절로 따라온다 — 상태별로 하나씩 덮을 필요가 없다.

**토큰 이름은 공개 API 다.** 지우거나 바꾸면 major 다. 그래서 **안 쓰는 토큰을 미리 만들지 않는다.**

### 강조색은 둘이다 — 채움과 읽히는 쪽

`--tx-color-primary` 하나가 **버튼 배경**과 **현재 메뉴 글자**를 겸하고 있었다. 두 요구가
반대로 당긴다: 채움은 그 위의 흰 글자를 위해 어두워야 하고, 글자로 쓰는 자리는 라이트에서
더 어둡고 다크에서 밝아야 한다.

겸하던 동안 기본 팔레트가 **AA 를 못 넘었다** — 흰 글자를 `blue-500` 위에 얹으면 3.68:1,
그 색을 글자로 쓰면 라이트 3.68:1 · 다크 2.84:1(AA 는 4.5:1).

| 토큰 | 무엇 | 라이트 / 다크 |
| --- | --- | --- |
| `--tx-color-primary` | **채우는 색** — 버튼 배경 · 스위치 트랙 · 체크 · 진행 막대 | `#2563eb` (다크도 같다) |
| `--tx-color-primary-strong` | **면 위에서 읽히는 색** — 현재 메뉴 · 탭 · 태그 글자 · 포커스 링 · 안내 아이콘 | `#1d4ed8` / `#60a5fa` |

**밝은 브랜드색(민트 · 파스텔)을 쓰는 소비자에게 특히 필요하다.** `--tx-color-primary` 만
바꾸면 버튼은 살아나고 메뉴 표시가 안 읽힌다 — `apps/site` 가 그 경우이고, 지금은 두 줄로 끝난다.

**어느 쪽인지는 계약이 지킨다.** `packages/ui/src/index.test.ts` 가 부품 토큰마다
채움/읽히는 쪽을 못 박아 두어서, 새 부품이 글자에 `--tx-color-primary` 를 쓰면 거기서 걸린다.
실제로 쓰는 컴포넌트가 생길 때 한 줄씩 늘린다.

전역 토큰은 12개다 (temp 기준 11개 + `--tx-color-primary-strong`) — `--tx-color-{primary,danger,muted,state,text,on-accent}` ·
`--tx-state-{hover,pressed}` · `--tx-focus-ring` · `--tx-focus-ring-offset` · `--tx-radius`.

### 2. 스타일시트는 하나만 낸다

```tsx
import "@txstack/ui/styles.css";
```

**컴포넌트가 자기 CSS 를 import 하지 않는다.** `styles.css` 에서만 모은다 —
그래야 SSR·번들러 환경에 따라 깨지는 경로가 생기지 않는다. 빌드가 `@import` 를 펼쳐
`dist/styles.css` 하나로 낸다. **순서가 곧 캐스케이드다** — 토큰 → 컴포넌트 순.

### 3. `@layer tx` 가 `className` 을 살린다

전부 `tx` 레이어에 넣는다. 이 한 줄이 핵심이다.

- **레이어 밖 CSS 는 레이어 안 CSS 를 특이도와 무관하게 무조건 이긴다.**
  그래서 순수 CSS · Sass · CSS Modules 를 쓰는 소비자는 **아무것도 안 해도** 덮어쓸 수 있다.
- **Tailwind 를 쓴다면 한 줄이 필요하다.** `tx` 는 preflight(`base`) 뒤, 유틸리티 앞이어야 한다.
  앞에 두면 preflight 가 버튼 배경·여백을 지우고, 뒤에 두면 `className` 이 안 먹는다.

  ```css
  @layer theme, base, tx, components, utilities;

  @import "tailwindcss";
  @import "@txstack/ui/styles.css";
  ```

### 4. `TxTheme` 은 폐기됐다

`TxClassBase` 같은 Tailwind 클래스 문자열 상수였다. 공개 API 로 두면 소비자가 그걸 받아서
할 수 있는 일이 **Tailwind 를 쓰는 것뿐**이라, "소비자가 무엇을 쓰든 상관없다" 는 전제와 어긋난다.

**이식 시 `TxTheme` 을 참조하는 컴포넌트는 그 참조를 CSS + 토큰으로 바꾼 뒤에 가져온다.**
`TxTheme` 자체는 새 저장소로 옮기지 않는다.

## 외부 의존 — 늘리지 않는다 (결정됨)

옛 패키지의 peer 에는 `framer-motion` 과 `react-router-dom` 이 있었다. **지금은 없고, 늘리지 않는다.**

- **`framer-motion`**(`TxModal` · `TxSlidePanel` · `TxLayout`) → **CSS transition 으로 옮긴다.**
  여닫히는 페이드·슬라이드에 애니메이션 라이브러리가 필요하지 않다. `dayjs` 를 걷어낸 것과 같은 판단이다.
- **`react-router-dom`**(`TxCard` · `TxDropMenu` · `TxContextMenu`) → **링크 컴포넌트를 주입받는다.**
  기본은 `<a>` 다. 이대로 옮기면 루트 배럴이 라우터를 끌어와 Next.js·TanStack Router 소비자가
  이 패키지를 못 쓴다. 주입이면 peer 가 늘지 않고 어느 라우터든 붙는다.

## 상태색은 네 갈래다 (결정됨)

`TxAlert` · `TxToast` · `TxTag` 가 **info · success · warning · danger** 네 갈래를
갖는데, 지금 전역 토큰에 **초록만 없다.** `TxJsonTree` 때 "새 전역색을 만들면 소비자가
브랜드색을 덮을 때 챙길 것이 는다" 며 미뤘던 것을 여기서 연다.

**`--tx-color-success` 하나만 늘린다.** `info` 는 `--tx-color-primary` 가 겸한다 —
브랜드색과 안내색을 가르고 싶은 자리가 있지만, 그 요구가 실제로 오기 전에 토큰을 늘리면
소비자가 챙길 것만 는다. 세 컴포넌트가 **같은 네 갈래를 쓴다.**

## CSS 계약 테스트 — 모든 컴포넌트가 갖는다

jsdom 에는 스타일시트가 없어 **렌더 결과로는 스타일을 볼 수 없다.** 그래서 `.css` 파일을
텍스트로 읽어 검사한다. `TxButton` · `TxFlex` 의 테스트가 본보기다.

- 색을 하드코딩하지 않고 토큰으로 내보내는가
- 다크모드 분기를 컴포넌트가 갖지 않는가 (토큰만 재정의하면 따라와야 한다)
- `styles.css` 에 실려 나가는가 (안 실리면 소비자에게 도달하지 않는다)
- `tx` 레이어 안으로 들어가는가 (레이어 밖이면 `className` 이 안 먹는다)
- 참조하는 전역 토큰이 전부 `tokens.css` 에 정의돼 있는가

**포털되는 팝업은 하나가 더 있다** — 앵커에 선언한 토큰은 팝업에 닿지 않으므로,
팝업 쪽에서 쓰는 토큰이 앵커에만 선언돼 있으면 실패한다.

## 이식 시 반드시 걷어낼 것

각 컴포넌트를 열 때 이것부터 확인한다.

- **`TxTheme` / Tailwind 클래스 문자열** — 위 `TxTheme` 절. CSS + `--tx-*` 토큰으로 옮긴다.
- **앱 전역(ambient) 타입** — 소비자 프로젝트에는 그 전역이 없다.
- **도메인 지식** — 블랙/문자/지갑/유저타입 등. props 로 받거나 잘라낸다.
- **`import.meta.env` 직접 참조** — Vite 아닌 소비자에서 깨진다. 옵션으로 받는다.
- **다른 Tx\* 컴포넌트로의 숨은 의존** — 배럴 import 라면 순환이 생길 수 있다.
- **default export** — 배럴의 `export *` 는 default 를 실어 나르지 않는다. named 로 바꾼다.

## 닫아 둔 결정

- [x] `TxForm.CheckBox` — **만들었다.** 라벨 배치는 맞출 것이 없었다. 대신 **이름을 잇지 않는 것**이
      판단이었다 — `TxCheckBox` 는 `label` 로 자기 이름을 이미 갖고 있어, 캡션까지 이으면 겹쳐 읽힌다.
- [x] **`tailwind-merge` 를 뗐다.** (결정됨)
      그것은 Tailwind 유틸리티끼리의 충돌을 정리하는 물건인데, **우리 컴포넌트는 자기
      `className` 에 Tailwind 를 하나도 싣지 않는다** — 전부 `tx-*` 와 CSS 변수다.
      훑어 보니 한 곳도 없었다(주석 속 예제뿐). 정리할 충돌이 애초에 없었던 셈이다.
      **소비자의 `className` 이 이기는 것은 `@layer tx` 덕분이지 `twMerge` 덕분이 아니었다** —
      레이어 밖의 규칙은 특성도와 무관하게 레이어 안을 이긴다. 하지 않는 일을 위해
      Tailwind 를 안 쓰는 소비자에게까지 의존을 지울 이유가 없다.
      **판단이 무너지지 않게 `index.test.ts` 가 문을 지킨다** — 컴포넌트 소스에서 주석을
      걷어낸 뒤 `className`·`cm()` 의 문자열 리터럴에 유틸리티가 섞이면 깨진다.
      이제 런타임 의존은 `clsx` 하나다.
- [x] **`TxInputLike` 는 공개하지 않는다.** (결정됨)
      `aria-expanded` 를 부모가 주입해야 정확한 부품이라, 열림 상태를 모르는 소비자가 쓰면
      **접근성이 거짓이 된다.** `TxPopup` 을 감춘 것과 같은 이유다 — 바르게 쓰려면 바깥이
      규약을 알아야 하는 것은 공개 API 가 아니라 부품이다. 요구가 실제로 오면 그때
      필요한 것을 옵션으로 받아 낸다. `index.test.ts` 가 이미 이 경계를 지키고 있다.
- [x] 2차 18개 중 무엇을 자를지 — **3차(이식) 목록에서 정했다.** 26개 중 24개를 이식한다.
- [x] **`TxPopup` 은 내부 부품으로 둔다 — 공개하지 않는다.** (결정됨)
      앵커에 붙어 뜨는 층에 임의의 내용을 넣고 싶은 자리는 실재한다 — 다른 라이브러리가
      `Popover` 로 파는 범주다. 그런데 지금 `TxPopup` 은 **포커스를 옮기지 않는다.**
      드롭다운·콤보박스·툴팁에는 맞지만 팝오버에는 틀리다 — 안에 폼이나 버튼이 있으면 포커스가
      들어가고 닫을 때 앵커로 돌아와야 한다. **`TxDropMenu` 가 답을 준다** — 메뉴는 규약상
      포커스가 메뉴 안으로 들어가므로, 그 요구가 공통 계층으로 가면 `TxPopover` 를 낼 재료가
      갖춰지고 메뉴만의 일로 남으면 계속 내부 부품이다.
      **메뉴를 올린 결과: 포커스는 `TxMenuShell` 에 남았다.** `TxPopup` 이 포커스를 옮기면
      드롭다운·콤보박스에서 타이핑이 끊기므로 공통 계층으로 올릴 수 없었다. 그러니 지금
      `TxPopup` 을 그대로 공개하면 소비자는 **포커스를 스스로 관리해야 하는 팝오버**를 받는다.
      대신 **겹쳐 뜬 팝업을 가리는 일(바깥 클릭·Escape 순서)은 `TxPopup` 으로 들어갔다** —
      팝오버로 낼 때 필요한 조각 하나는 갖춰진 셈이다.
      **결정: 계속 내부 부품이다.** 포커스 관리를 옵션(`trapFocus`·`returnFocus`)으로 받아
      `TxPopover` 로 내는 길도 있었지만, **아직 그것을 요구하는 소비자가 없다.**
      쓰는 자리를 모르는 채로 옵션을 먼저 만들면 그 옵션이 맞는지 확인할 길이 없고,
      한 번 공개한 API 는 되돌릴 수 없다. 요구가 실제로 생기면 그때 낸다 — 그때
      필요한 재료(겹친 팝업 가리기)는 이미 `TxPopup` 안에 있다.
      **나중에 공개해서 스토리를 만들게 되면 첫 줄에 이것부터 적는다** — 혼자 쓰는 컴포넌트가
      아니라 비슷한 것을 만들 때 바탕으로 쓰는 부품이라는 것. 그러지 않으면 소비자가
      이걸로 무엇을 해야 하는지 모른다.

- [x] **바탕 부품의 정책을 물려받는다는 설명을 나머지 스토리에도 넣었다.** (결정됨)
      `TxDropdown` · `TxCombobox` · `TxDayPicker` 에 같은 절을 넣고, `TxTooltip` 것에는
      나중에 생긴 성질(**겹쳐 떠도 서로를 가리지 않는다**)을 더해 다섯이 같은 목록을 갖는다.
      **`TxPopup` 을 감춰 둔 대가**가 여기 있다 — 소비자는 그 이름을 못 보므로, 그것이 주는
      성질을 각 스토리가 대신 말해 주지 않으면 **어디서 오는 동작인지 알 길이 없다.**
