# txstack 문서

> **여기가 진입점이다.** 이 저장소가 무엇을 만드는지, 어디까지 왔는지, 다음에 무엇을 할지가 이 한 장에 있다.
> 상세로 내려갈 때는 아래 "문서 지도"를 따라간다.

## 1. 무엇을 만드는가

**여러 프로젝트에서 재사용할 수 있는 범용 React 라이브러리 세트**를 만든다. npm 에 배포한다.

목표는 "컴포넌트를 모아두는 것"이 아니다. **여러 프로젝트를 동시에 오갈 때 매번 다시 배우지 않아도 되는 것** —
같은 이름, 같은 props, 같은 커스터마이징 방법. 멀티 작업의 인지 비용을 줄이는 게 이 라이브러리의 존재 이유다.

`packages/*` 의 기본 기능은 **이미 구현되어 있다.** 그래서 지금 하는 일은 새로 만들기가 아니라,
**하나씩 열어보고 결함·불필요한 것을 정리해서 배포 가능한 수준으로 올리는 것**이다.

## 3. 문서 지도

한 주제에 관한 모든 문서는 **번호 폴더 하나** 안에 있다. 001 을 파악하려면 `001_ui/` 만 열면 된다.

```
docs/
├─ README.md              ← 지금 이 문서. 진입점
├─ 00_foundation/         ← 상시 규약 (번호 흐름과 무관)
├─ 001_ui/
│  ├─ README.md           ← 이 주제의 진입점: 정의 · 현재 상태 · 다음 할 일
│  ├─ 10_requirements.md  ← 무엇을 / 왜. 수용 기준
│  ├─ 20_design.md        ← 공개 API 형태. 예제 코드 먼저, 결정 근거와 버린 대안
│  ├─ 30_tasks.md         ← 컴포넌트별 진행 보드 (플로우 6단계)
│  ├─ 40_verification.md  ← 검증 항목 · 절차 · 결과
│  └─ components/         ← 컴포넌트 하나당 명세 1장 (플로우 S1 산출물)
├─ 002_route_meta/  003_hooks/  004_network/   ← 각각 30_tasks.md + items/
├─ 901_storybook/   902_testing/  903_docs_site/  904_claude_guide/
└─ temp/                  ← 이전 문서 (참고용)
```

**작업 항목 문서와 인덱스는 미리 다 만들어 둔다.** 창을 나눠 진행하려면 열 문서가 이미 있어야 한다.
각 항목 문서에는 **자동 수집한 현재 코드 인벤토리**와 **착수 전에 알아야 할 것**이 미리 채워져 있다.

**내용은 미리 채우지 않는다.** `10 → 20 → 30 → 40` 순서로 내려가고, 앞 단계가 비어 있으면 뒤 단계로 넘어가지 않는다.
🤝 표시된 절은 사용자 승인 없이 채우지 않는다.

## 4. 작업 방식 (가장 중요)

**전체 틀은 항상 사용자가 숙지한다.** Claude 에게 "다 만들어" 라고 하는 프로젝트가 아니다.

| 무엇                                             | 담당           |
| ------------------------------------------------ | -------------- |
| 요구사항 정의, 공개 API 형태 결정, 구조 판단     | 🤝 함께 합의   |
| 첫 구현 (그 패턴을 처음 만드는 코드)             | 🧑 사용자 직접 |
| **결과물 확인** — "내가 원하던 물건인가" (§5)    | 🧑 사용자 직접 |
| 반복 구현 (합의된 패턴을 N번 반복), 테스트, 잡일 | 🤖 Claude      |

규칙:

1. **설계는 예제 코드로 먼저 합의한다.** "소비자가 이렇게 쓴다" 를 `20_design.md` 에 적고, 그게 자연스러운 방향으로 API 를 맞춘다.
2. **🧑 job 은 Claude 가 대신 하지 않는다.** 막히면 설명·리뷰·대안 제시까지만 한다.
3. **판단이 필요한 job 은 사용자 승인 없이 넘어가지 않는다.**
4. Claude 가 구현한 것도 사용자가 리뷰로 숙지한다. 리뷰가 안 된 코드는 완료가 아니다.

상세: [00_foundation/02_WORKFLOW.md](00_foundation/02_WORKFLOW.md)

## 5. 어떻게 진행하는가 — 컴포넌트 플로우

**컴포넌트(또는 훅) 하나가 작업 항목이다.** 그 하나를 6단계로 끝까지 올린다.

```
TxSpinner ─ S1 문서 → S2 구현 → S3 테스트 → S4 스토리북 → 🧑 확인 → S5 문서사이트 → S6 에이전트가이드 ─▶ 완료
TxButton  ─ S1 → S2 → S3 → S4 → 🧑 → S5 → S6 ─▶ 완료
                    ▲                 │
                    └── 2차 개선 ─────┘
```

**이 화살표는 실제로 돌았다.** 파일럿 2종이 게이트를 통과한 뒤 **스타일 방침이 바뀌어 `S2` 로 되돌아갔다**
(2026-08-25 · [001_ui/20_design](001_ui/20_design.md)). 되돌아가는 게 이 플로우의 기능이다.

계층별로 하면(전부 문서 → 전부 구현 → …) 끝까지 가는 게 하나도 없다. 그래서 **수직으로 자른다.**

**`S1~S4` 가 1차(🤖), 그다음이 🧑 사용자 확인 게이트다.** 기계가 판정할 수 있는 것(타입·회귀·계약)은
1차에서 다 걸러지지만, **"내가 원하던 물건인가"는 직접 만져봐야 안다.** 그래서 문서화(S5·S6) 전에 멈춘다 —
2차 개선에서 props 하나만 바뀌어도 사이트와 가이드를 다시 써야 하기 때문이다.

도구도 그 선을 따른다. **vitest = 🤖 의 자동 검증 / Storybook = 🧑 가 직접 보는 자리.**
Storybook 에는 스토리가 있는 것을 전부 싣고, **무엇이 검증됐는지는 진행 보드가 말한다.**

**지금은 양식이 전부 미정이므로 파일럿으로 만든다.**

| 파일럿              | 목적                                            |
| ------------------- | ----------------------------------------------- |
| **1차 `TxSpinner`** | 플로우 절차 자체를 확정 (표면이 가장 작다)      |
| **2차 `TxButton`**  | 커스터마이징 방식과 props·콜백 이름 규칙을 확정 |
| 3차 이후            | 🤖 반복 + 사용자 리뷰                           |

상세: [00_foundation/06_COMPONENT_FLOW.md](00_foundation/06_COMPONENT_FLOW.md)

> 결함 7건 중 무거운 둘 — **폼 안 버튼이 전부 폼을 제출하던 것**, **텍스트 버튼에 포커스 링이 없던 것.**

> `tx-spinner` 클래스 하나 + 토큰 둘. **컴포넌트 CSS 에 `.dark` 분기가 한 줄도 없이** 다크모드가 따라온다.

> **게이트는 실제로 일했다.** 1차 확인 과정에서 4건이 나와 통과 전에 고쳤다 — 컨트롤이 죽어 있던 스토리,

> **세 번째가 방향을 바꿨다.** "클래스 문자열로는 소비자가 색 하나를 못 바꾼다" 가
> **Tailwind → 자체 CSS 전환**([001_ui/20_design](001_ui/20_design.md))의 직접 증거가 됐다.
> 그래서 파일럿 2종은 **`↩` 로 되돌아가 S2~S4 를 다시 돈다.**

## 8. 새 세션을 여는 법

주제 하나(또는 그 하위 단계)마다 **새 대화를 연다.** 컨텍스트가 섞이지 않고, 끝나면 닫으면 된다.

첫 프롬프트는 이 형태면 충분하다.

```
docs/README.md 와 docs/001_ui/20_design.md 를 읽고 001-TxButton-S2 ~ S4 (2차) 를 진행해줘.
```

각 번호 폴더의 `README.md` 는 **자립적이다.** 그 주제를 진행하는 데 필요한 링크·현황·다음 할 일이 그 안에 있다.
