# 903 — 문서 사이트

> **한 줄 정의**: **예제와 코드**를 제공하는 문서 사이트.

## 왜 만드는가

Storybook 은 "이 컴포넌트가 어떻게 생겼나" 를 보여준다. 하지만 소비자의 첫 질문은 그게 아니다.

- 설치하고 나서 **무엇을 먼저 해야 하나** (`@txstack/ui/styles.css` import 같은 것)
- `route-meta` 와 `useUrlQuery` 를 **함께** 쓰면 어떤 모양이 되나
- 목록 화면 하나를 처음부터 끝까지 만드는 코드는 어떻게 생겼나

Storybook 이 답하기 어려운 건 **여러 패키지를 걸친 흐름**과 **설치·설정 안내**다.
문서 사이트는 그걸 맡는다.

## 현재 상태

**없다.** 아무것도 만들어져 있지 않다.

## 핵심 미결: Storybook 과 통합할 것인가

요청에 명시된 열린 질문이다. 세 가지 선택지가 있다.

| 안                                         | 장점                                                            | 단점                                                              |
| ------------------------------------------ | --------------------------------------------------------------- | ----------------------------------------------------------------- |
| **A. Storybook 하나로 통합** (MDX 로 문서) | 관리 지점 하나. 컴포넌트 예제와 코드가 같은 곳. 배포도 한 번    | 4개 패키지 중 `ui` 만 잘 맞는다. 훅·네트워크 문서를 담기 어색하다 |
| **B. 별도 사이트 + Storybook 링크**        | 패키지 4종을 대등하게 다룰 수 있다. 가이드 흐름을 자유롭게 구성 | 관리 지점 둘. 예제 코드가 두 곳에 갈라질 위험                     |
| **C. 별도 사이트에 Storybook 임베드**      | 입구는 하나, 컴포넌트 상세는 Storybook 이 담당                  | 빌드·배포 파이프라인이 가장 복잡                                  |

**현재 권고: B 또는 C.** 이유 —
`ui` 는 4개 패키지 중 하나일 뿐이고, `route-meta` · `hooks` · `network` 는 시각 컴포넌트가 아니다.
Storybook 에 다 넣으면 "컴포넌트 카탈로그" 라는 Storybook 의 강점이 흐려진다.
다만 **관리 비용이 두 배가 되므로, `901` 의 문서화 수준이 정해진 뒤에 결정한다.**

## 컴포넌트 플로우에서의 위치

이 트랙은 **`S5` 단계의 양식을 소유**한다 → [06_COMPONENT_FLOW.md](../00_foundation/06_COMPONENT_FLOW.md)

- 페이지를 한꺼번에 쓰지 않는다. **각 컴포넌트·기능의 S5 에서 한 장씩 쌓인다**
- 내용의 원본은 `001_ui/components/<Name>.md` (S1) 다. 사실이 갈리면 S1 을 고치고 여기를 맞춘다
- 파일럿 1차(`TxSpinner`)에서 **사이트의 최소 골격 + 한 페이지**를 만든다. 도구 선택도 그때 결정된다
