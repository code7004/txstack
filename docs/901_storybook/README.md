## 확정된 것 (2026-08-25) — 자동화하지 않는다

**Storybook 은 사람이 보는 자리고, 자동 검증은 vitest 가 맡는다.** 이 경계는 결정됐다.

- `play` 함수를 쓰지 않는다. `@storybook/addon-vitest` 를 도입하지 않는다.
- 파일럿에서 **기술적으로 가능하다는 것은 확인했다** — Storybook 10 코어에 `storybook/test` 와
  `instrumenter` 가 들어 있어 추가 설치 없이 `play` 가 돌고, 실제로 **jsdom 이 못 잡은 D1 을 잡았다**
  (`expect(11).toBe(12)`). 그래도 안 쓴다.
- **이유**: 여기까지 자동화하면 사람이 볼 자리가 사라진다. 확인 화면이 초록 체크로 덮이면
  "통과했네" 하고 넘어가게 되고, 그러면 게이트가 일을 안 한다. 자동 검증을 늘려야 하면 `902` 쪽을 늘린다.

이 결정으로 `901-03` 의 "S1 감사의 시각적 결함을 스토리로 재현·반증할 것인가" 는 **닫혔다** —
재현은 하되(그게 스토리다) **단언하지 않는다.**

## 왜 만드는가

컴포넌트 라이브러리에서 "쉬운 사용법"은 문장으로 증명되지 않는다. **눈으로 보고 만져봐야** 증명된다.
Storybook 은 두 역할을 겸한다.

1. **소비자용 가이드** — 어떤 컴포넌트가 있고, props 를 바꾸면 어떻게 변하는지
2. **개발용 작업대** — 앱을 띄우지 않고 컴포넌트 하나만 격리해서 만들고 확인

두 번째가 첫 번째보다 먼저 온다. **작업대로 쓰이지 않는 Storybook 은 금방 낡는다.**

## 현재 코드 자산

- `apps/storybook/` (private, 배포하지 않음) — Storybook 10 + `@storybook/react-vite`
- `pnpm storybook:dev` (:6310) / `pnpm storybook:build`
- 스토리는 컴포넌트 폴더 안에 `*.stories.tsx` 로 둔다 — 일부 컴포넌트에만 존재
- `@storybook/addon-docs` 설치됨
- **테마 토글이 이미 있다** — `preview.tsx` 의 툴바(☀/🌙)가 `<html class="dark">` 를 켠다. 다크 검증은 이걸로 한다

### 다크가 어디까지 먹는가 (2026-08-25 확인)

| 영역                                      | 무엇을 따라가나        |
| ----------------------------------------- | ---------------------- |
| **스토리 캔버스 (컴포넌트)**              | **툴바 토글** ☀/🌙     |
| autodocs 문서 페이지 (배경·본문·props 표) | 아무것도 — 항상 라이트 |
| Storybook UI (사이드바·툴바)              | 브라우저/OS 설정       |

**컴포넌트 검증에 필요한 캔버스는 잘 동작한다.** 나머지 둘은 그대로 둔다.

#### 문서 페이지를 다크로 만들려다 되돌렸다

`src/tailwind.css` 에서 `.dark .sbdocs-*` 로 표면을 칠해 봤다. 배경은 바뀌었지만 **두 가지가 깨졌다.**

1. **글자가 흐릿해졌다.** `addon-docs` 는 배경·본문·표·코드 색을 자기 테마 객체로 한 벌로 칠하는데,
   내가 셀렉터 몇 개만 덮으니 나머지가 밝은 테마 색으로 남았다. **한 벌로 바꿔야 하는 걸 조각으로 덮은 것.**
2. **그리드 툴이 안 보였다.** 그리드는 `.docs-story` 에 `rgba(130,130,130,0.5)` 그라디언트로 그려지는데,
   그 위에 단색 배경을 얹으면 묻힌다.

**되돌렸다.** 제대로 하려면 CSS 가 아니라 **`parameters.docs.theme` 에 Storybook 테마 객체**를 주는 게 맞다
(`storybook/theming` 의 `themes.dark`). 다만 그건 정적이라 툴바 토글을 못 따라간다 —
**토글과 동기화하려면 커스텀 docs container 가 필요하다.** `901-05`(문서화 수준)와 함께 판단한다.

> **교훈: 애드온이 한 벌로 칠하는 표면을 CSS 로 조각조각 덮지 않는다.**
> 그리드처럼 배경에 기대는 다른 기능까지 같이 깨진다.

**Storybook UI 는 툴바 토글과 동기화되지 않는다.** 매니저는 별도 앱이고 런타임 테마 교체를 지원하지 않는다.
기본값이 OS 설정을 따라간다 (다크 선호 → `rgb(27,28,29)`, 라이트 선호 → `rgb(246,249,252)`. 실측).
항상 다크로 고정하려면 `.storybook/manager.ts` 에 `addons.setConfig({ theme: themes.dark })` 한 줄이면 되지만
**재시작이 필요해 검증하지 못했고, 기본 동작과 중복이라 두지 않았다.**

## 상태

**미착수 (`10_requirements.md` 없음). 단, 파일럿 1차의 결과물이 나와 있다.**

### 파일럿 1차 `TxSpinner` S4 에서 관찰된 것 (2026-08-25)

실물: `packages/ui/src/TxSpinner/TxSpinner.stories.tsx` (`Feedback/TxSpinner`, 스토리 5개).
아래는 `901-02`~`901-05` 의 🤝 결정 재료이며, **결정 자체는 아니다.**

**0) 만질 수 없는 스토리는 확인 도구가 아니다 — `901-03` 필수 구성의 1순위 후보.**
첫 판은 스토리 5개를 전부 `render: () => …` 로 짰다. **args 가 무시돼서 컨트롤 패널이 죽어 있었다.**
사용자가 게이트에서 바로 지적한 것이 이것이다 — "params 넣어서 테스트 하는 게 없는데".

> **컴포넌트마다 `플레이그라운드` 스토리를 하나 둔다.** `render: (args) => …` 로 받고 `args` 를 채워
> 컨트롤이 처음부터 값이 든 채로 보이게 한다. (`args` 를 비우면 컨트롤이 "Set string" 버튼으로 접혀
> 패널이 비어 보인다.)
>
> **비교용 스토리는 `controls: { disable: true }` 로 컨트롤 탭을 없앤다.** 죽은 손잡이를 보여주지 않는다.
>
> **눈에 안 보이는 prop 은 결과를 화면에 적는다.** `decorative`·`aria-label` 은 토글해도 시각 변화가 없어
> "스크린리더: …" 한 줄을 렌더에 넣었다. 이게 없으면 확인이 불가능하다.

여기서 실제로 결함이 하나 나왔다 — `decorative` 가 소비자의 `aria-label` 을 못 버리고 있었다.
**S3 테스트는 단독 케이스만 봐서 놓쳤고, 사람이 두 손잡이를 같이 돌리자 나왔다.** 게이트의 값이 여기 있다.

**1) 스토리는 props 목록이 아니라 판단 기준을 보여주는 게 낫다 — `901-03` 에 직결.**
`크기` 스토리에 담은 것은 크기 값들의 나열이 아니라 **"부모 `text-*` 에 맡길 것인가, `size` 로 줄 것인가"** 다.
소비자가 실제로 하는 고민이 그거다. props 하나에 스토리 하나씩 붙이면 개수만 늘고 답은 안 나온다.

**2) CSS 가 걸린 결함의 검증처는 여기다 — `901`/`902` 경계선.**
`TxSpinner` 의 최대 결함 D1 은 CSS 캐스케이드 문제라 **jsdom 테스트로는 잡히지 않았다**([902 README](../902_testing/README.md)).
S4 에서 실제 브라우저 + 실제 Tailwind 로 6개를 실측해서야 증명됐다 — 전부 정사각형, 폰트 크기 상속 정상.

> 갈라지는 선: **테스트(`902`)는 결함의 원인(속성·클래스)을 자동으로 지키고,
> 스토리(`901`)는 결과(렌더된 모습)를 사람 눈앞에 놓는다.** 단언은 하지 않는다 — 위 "확정된 것" 참고.
> `901-03` 의 "필수 구성"에는 **"S1 감사에서 나온 시각적 결함을 눈으로 확인할 수 있는 스토리"** 가 후보다.

**3) `docs.description.component` 는 주의점부터 적었다 — `901-05` 재료.**
소비자가 틀리는 지점은 S1 감사에 이미 적혀 있다(`TxSpinner` 는 D4 — `size` 에 클래스를 주면 무효).
설명 첫머리를 소개말이 아니라 **그 함정**으로 채우면 autodocs 만으로도 상당 부분 커버된다.
MDX 가 필요한지는 이 방식으로 부족할 때 판단하면 된다.

**4) 그룹은 `Feedback/` 을 썼다** — `TxLoading` · `TxClipboardButton` 과 같은 자리. 이로써 **그룹 없는 스토리는 0건**이 됐다 (`901-01`).

### 파일럿 2차 `TxButton` S4 에서 관찰된 것 (2026-08-25)

**5) 스토리는 기능이 아니라 "경우" 로 가른다 — `901-03` 필수 구성 재료.**
처음에는 `커스터마이징` 하나에 `className`·`theme`·`TxThemeProvider` 를 다 쌓았다.
**범위가 다른 이야기를 한 화면에 올리니 "나는 지금 어느 경우인가" 가 안 보였다.**
사용자가 게이트에서 지적해 `Customizing - class` / `Customizing - Provider` 로 나눴다.

> 소비자는 **자기 상황부터 고르고** 들어온다 — "이 버튼 하나만" 인지 "앱 전체" 인지.
> 손잡이를 다 보여주는 스토리 하나보다, 상황별로 나눈 둘이 낫다.
> `901-03` 의 "필수 구성" 을 **prop 목록이 아니라 경우의 목록**으로 쓰는 쪽을 검토한다.

**6) 함정은 ✗/✓ 를 나란히 놓는다.**
`className="bg-yellow-500"` 이 평상시만 노랑이 되는 함정(`hover:`·`dark:` 는 조건이 달라 안 지워진다)을
**틀린 것과 맞는 것을 나란히** 배치해 마우스만 올리면 드러나게 했다. 설명 문단보다 빠르다.
