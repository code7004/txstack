# 006 · 기존 프로젝트에 적용하기

**배포 전에 완성도를 올린다.** 네 패키지를 npm 에 올리기 전에, 원래 이 코드가 나온
세 프로젝트에 **되돌려 넣어 본다.**

판정 기준은 [docs/README](README.md) 와 같다 — **네 번째 프로젝트가 그대로 설치해 쓸 수 있는가.**
그 답은 책상에서 안 나온다. 진짜 화면에 붙여 봐야 나온다.

---

## 세 프로젝트는 이제 소비자다

`black-message` · `usertics` · `chain-wallet-service` 는 **읽기 전용 원본이었다.**
거기서 공통분모를 뽑아 네 패키지를 만들었으니, 그 역할은 끝났다.

**이제는 소비자다. 고치는 대상이다.** 이전 규칙("수정하지 않는다, 읽기만 한다")은
[CLAUDE.md](../CLAUDE.md) 에서 바꿨다.

- **브랜치를 파고 작업한다.** `main` 에 직접 넣지 않는다
- **패키지와 그 프로젝트를 한 커밋에 담지 않는다.** 저장소가 다르니 당연하지만, 한 작업에서
  양쪽을 동시에 고치게 되므로 의식하지 않으면 순서가 엉킨다
- 이식 시절의 원본 코드가 필요하면 `git show origin/legacy:<경로>` 로 꺼내 읽는다.
  `legacy` 브랜치는 **여전히 읽기 전용**이다

## 작업 자리

**저장소 넷이 `~/work` 에 나란히 있다.** 외장(`/Volumes/Workspace`)은 더 쓰지 않는다 —
이유는 [900_setup](900_setup.md) 의 exFAT 절에 있다.

```
~/work/txstack                 이 저장소 (패키지 · 문서)
~/work/black-message           소비자 — apps/frontend
~/work/usertics                소비자 — apps/frontend
~/work/chain-wallet-service    소비자 — apps/portal
```

**세션은 `~/work/txstack` 에서 열고, 대상 프로젝트를 디렉터리로 추가한다.** 양쪽을
동시에 고치게 되므로 둘 다 보여야 한다 — 패키지의 결함은 txstack 에서, 화면은
프로젝트에서 고친다.

**다만 그 프로젝트의 관습이 이 저장소의 관습을 이긴다.** 프로젝트에 자기 `CLAUDE.md` 나
`.claude/` 가 있으면 **그것을 먼저 읽는다.** 여기 규약(커밋 메시지 형식 · 폴더 구조 ·
명명)은 txstack 것이고, 소비자 코드에 그것을 밀어 넣으면 그 프로젝트 사람이 읽을 수 없는
코드가 된다.

### 세 프로젝트의 프론트

셋 다 **React 19 · react-router 7 · Tailwind 4 · ag-grid** 다 — 패키지의 peer 범위
(`react >=18` · `react-router-dom >=6`)에 전부 든다.

| 프로젝트               | 앱              | 화면(pages)       | tsx/jsx | axios     |
| ---------------------- | --------------- | ----------------- | ------- | --------- |
| `black-message`        | `apps/frontend` | 10                | 103     | `^1.8.3`  |
| `chain-wallet-service` | `apps/portal`   | `pages` 폴더 없음 | 92      | 앱엔 없음 |
| `usertics`             | `apps/frontend` | 2                 | 158     | `^1.9.0`  |

**`black-message` 를 첫 타자로 권한다.** 화면 경계가 10개로 뚜렷해서 "첫 화면 하나" 를
고르기 쉽고, axios 와 ag-grid 를 다 써서 **래퍼와 서브패스를 한 번에 검증**한다.
규모도 거의 가장 작다.

## 붙이는 방법 — 첫 프로젝트는 tarball

| 방식                          | 무엇이 검증되나                                                                  | 반복 속도                      |
| ----------------------------- | -------------------------------------------------------------------------------- | ------------------------------ |
| **tarball** (`pnpm pack`)     | `exports` 맵 · `files` · `.d.ts` · 서브패스 · peer 해결 — **배포판과 같은 경로** | 느리다 (고칠 때마다 다시 pack) |
| 링크 (`pnpm link` · `file:`)  | 런타임 동작만                                                                    | 빠르다                         |
| 소스 alias (`apps/site` 방식) | 런타임 동작만. `dist` 를 통째로 건너뛴다                                         | 가장 빠르다                    |

**첫 프로젝트는 tarball 로 붙인다.** 포장 결함(`exports` 가 안 잡힘 · 타입이 안 따라옴 ·
서브패스가 해결 안 됨)은 **진짜 설치일 때만 드러나고**, 세 프로젝트를 다 옮긴 뒤에 발견하면
세 번 다시 손대야 한다.

포장이 한 번 검증되고 나면 이후 프로젝트는 링크로 빠르게 돌려도 된다.

```sh
# txstack 저장소에서
pnpm build
pnpm -r --filter "./packages/*" exec pnpm pack --pack-destination /tmp/txpack
```

```sh
# 대상 프로젝트에서
pnpm add /tmp/txpack/txstack-ui-0.1.0.tgz /tmp/txpack/txstack-hooks-0.1.0.tgz
```

심볼릭 링크가 아니라 **실제 압축 해제**라 React 중복 · peer 해결 · 타입 로딩이
배포판과 같게 돈다.

**포장 검증은 끝났다** (`black-message`, 2026-09-03). tarball 로 실제 설치해 진입점 8개
(`ui` 의 `index` · `aggrid` · `daypicker` · `styles.css`, `hooks` 의 `index` · `router`,
`axios` 의 `index` · `singleton`, `route-meta` 의 `index`)가 전부 **해석되고 · 타입이 따라오고 ·
Node 에서 런타임 로드까지 되는 것**을 확인했다. peer 경고 0건. `@txstack/axios` 는 맨 Node 에서
로드돼 React 를 모른다는 것도 같이 확인됐다.

**그래서 이후는 링크로 간다.** tarball 을 고집한 이유(포장 결함은 진짜 설치일 때만 드러난다)는
소진됐고, 남은 것은 반복 속도다.

### 링크로 붙일 때 — React 가 두 벌 되는 것을 막아야 한다

```jsonc
// 소비자 package.json — 상대경로라 Windows·Mac 양쪽에서 돈다
"@txstack/ui": "link:../../../txstack/packages/ui"
```

`link:` 는 **소스 폴더로 가는 심볼릭 링크**다. 그래서 링크된 패키지 안에서 찾는 `react` 는
소비자 것이 아니라 **txstack 쪽 `node_modules`** 로 잡힌다. 버전이 같아도 경로가 다르면
별개 인스턴스라 첫 컴포넌트를 붙이는 순간 `Invalid hook call` 이 난다 —
**원인이 화면 코드에 없어서 찾기 어려운 종류다.**

```ts
// 소비자 vite.config.ts
resolve: {
  dedupe: ["react", "react-dom", "react-router-dom", "ag-grid-community", "ag-grid-react"];
}
```

상태를 들고 있는 것만 모으면 된다 — 훅·컨텍스트(React · 라우터)와 전역 등록
(`ag-grid` 의 `ModuleRegistry`). npm 배포본으로 바꾸면 어차피 한 벌이라 이 설정은 무해하게 남는다.

**링크의 진짜 위험은 경로가 아니라 `dist` 를 다시 안 빌드하는 것이다.** 소스를 고치고
`pnpm build` 를 잊으면 소비자는 옛 코드를 보면서 "왜 안 고쳐지지" 를 한다. watch 를 띄워 둔다.

```sh
pnpm build:watch   # 네 패키지를 동시에 지켜본다. ui 는 CSS 까지 다시 낸다
```

### 커밋하면 안 되는 것

**로컬 경로는 소비자의 `main` 에 올리지 않는다.** `black-message` 는 EC2 에서
`pnpm install --frozen-lockfile` 을 **워크스페이스 루트에** 돌리기 때문에, 락파일에 로컬
경로가 있으면 그 경로가 서버에 없어 배포가 막힌다. `--frozen-lockfile` 이라 서버에서만
빼는 것도 안 된다.

서버는 `origin/main` 을 pull 하므로 **적용 브랜치에 머무는 동안은 안전하다.**
머지 전에 npm 버전으로 바꾼다.

### 붙인 직후 할 일

```ts
import "@txstack/ui/styles.css"; // 이 한 줄이 없으면 아무 스타일도 없다
```

**Tailwind 를 쓰는 소비자는 레이어 순서를 먼저 못박아야 한다.** 안 그러면 `tx` 레이어가
Tailwind 레이어들 **뒤에** 선언돼, 화면에서 준 유틸리티 클래스가 부품 CSS 에 진다.
순서는 선언 순서로 정해지므로 `styles.css` 를 JS 에서 import 하면 그 순서가 번들러 손에
넘어간다 — **CSS 진입 파일 안에서 `@import` 로 가져오고 위에 순서를 적는다.**

```css
/* 소비자의 Tailwind 진입 CSS */
@layer theme, base, tx, components, utilities;

@import "tailwindcss";
@import "@txstack/ui/styles.css";
@import "./txstack-theme.css"; /* 토큰 재정의 */
```

토큰 재정의는 **레이어 밖에** 둔다. 패키지 토큰이 `@layer tx` 안에 있어서, 레이어 없는
규칙이 순서와 상관없이 이긴다.

겉모습은 **부품 CSS 를 덮지 않고 토큰만 다시 정의한다.** 방법은 사이트의
`Guide › Tokens` 와 [apps/site/src/theme.css](../apps/site/src/theme.css) 가 실물 예제다.

**강조색은 둘이다** — 채우는 `--tx-color-primary` 와 면 위에서 읽히는
`--tx-color-primary-strong`. 브랜드색이 밝으면 둘을 각각 줘야 한다.

## 프로젝트 하나의 순서

**한 프로젝트를 끝까지 관통한 뒤 다음으로 간다.** 세 개를 동시에 열지 않는다.

| 단계 | 하는 일                                                                                         | 담당 |
| ---- | ----------------------------------------------------------------------------------------------- | ---- |
| 0    | **대상 화면 선정** — **목록 하나 + 폼 하나**부터. Storybook 의 `Recipes` 가 이미 그 둘을 덮는다 | 🤝   |
| 1    | **붙인다** — 설치 · `styles.css` + 레이어 순서 · 토큰 정의. 링크면 `dedupe` 까지                | 🤖   |
| 2    | **첫 화면을 교체한다** — 여기서 그 프로젝트의 관습이 정해진다                                   | 🧑   |
| 3    | **나머지를 같은 모양으로** — 첫 화면이 본보기다                                                 | 🤖   |
| 4    | **드러난 것을 기록한다** — 아래 "무엇을 기록하나"                                               | 🤖   |
| 5    | **그 프로젝트의 빌드·테스트가 통과하는지**                                                      | 🤖   |
| 6    | **확인 — 여기서 멈춘다.** 사용자가 직접 돌려 보고 지시한다                                      | 🧑   |

**6단계를 건너뛰지 않는다.** 화면이 실제로 도는 것을 사람이 봐야 다음 프로젝트로 간다.

### 어느 프로젝트부터

사용자가 정한다. 판단 기준만 적어 둔다.

- **화면 수가 적은 쪽이 먼저다** — 첫 프로젝트는 포장 결함을 찾는 자리라 오래 걸린다
- **목록 + 폼이 주력인 쪽** — `Recipes` 가 덮는 형태라 검증이 빠르다
- `ag-grid` 를 쓰는 프로젝트는 **서브패스 검증을 겸한다.** 다만 첫 타자로는 무겁다

## 무엇을 기록하나

**적용의 산출물은 옮긴 화면이 아니라 드러난 것들이다.** 세 갈래로 나뉘고 가는 곳이 다르다.

| 무엇                                                  | 어디로                                               |
| ----------------------------------------------------- | ---------------------------------------------------- |
| **포장 결함** — `exports` · `.d.ts` · peer · 서브패스 | 그 자리에서 고치고 **아래 표**에                     |
| **토큰·API 부족** — 부품 CSS 를 덮고 싶어지는 순간    | 해당 부품 문서 `docs/001_ui/NNN_*.md`                |
| **도메인이 패키지로 새려는 순간**                     | **아래 표에 "거절" 로.** 거절한 기록이 경계를 지킨다 |

부품 클래스에 손대고 싶어지면 그건 **토큰이 부족하다는 신호**다. 덮어쓰지 말고 토큰을 연다.
[005_site](005_site.md) 의 "만들며 드러난 것" 이 같은 형식의 본보기다.

### 드러난 것

| 무엇                                                                                                | 어디서                      | 어떻게 했나                                                                                                                |
| --------------------------------------------------------------------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **`TxAgGridOption` 이 루트 배럴에 없다.** 소비자가 `@txstack/ui` 에서 꺼내려다 `TS2305` 를 맞는다   | `black-message` 목록 화면   | **열린 채로 둔다** — 아래 "타입만 루트로 올릴 것인가"                                                                      |
| **로컬 링크로 붙이면 React 가 두 벌 로드된다.** 링크된 패키지 안의 `react` 는 txstack 쪽으로 잡힌다 | `black-message` 붙이는 단계 | 소비자 `vite.config.ts` 에 `resolve.dedupe`. **패키지 결함이 아니라 링크 방식의 성질**이라 아래 "링크로 붙일 때" 에 적었다 |
| **레이어 순서를 소비자가 못박아야 한다.** 안 하면 `tx` 가 맨 뒤에 붙어 부품이 유틸리티를 이긴다     | `black-message` 붙이는 단계 | "붙인 직후 할 일" 에 `@layer` 한 줄을 추가했다. `styles.css` 를 JS 로 import 하면 순서가 번들러 손에 넘어간다              |

#### 타입만 루트로 올릴 것인가 — 열린 자리

무거운 선택적 의존은 서브패스로 가른다는 규칙이 **값에는 맞는데 타입에도 맞는지**가
아직 안 정해졌다. 소비자가 목록 화면을 쓰면 이렇게 된다:

```ts
import { TxAgGrid, type TxAgGridOption } from "@txstack/ui/aggrid"; // 지금
import { type TxAgGridOption } from "@txstack/ui"; // 이렇게 쓰려다 TS2305
```

**타입은 런타임 무게가 0이다.** 값(`TxAgGrid`)은 서브패스에 두더라도 타입만 루트에서
재수출하면, 소비자는 "이 심볼이 어느 진입점에 있는지" 를 외우지 않아도 된다.

반대 논리도 있다 — **한 부품의 값과 타입이 다른 곳에서 나오면 그게 더 헷갈린다.**
서브패스로 통일하는 쪽이 규칙이 하나다.

**두 번째 프로젝트에서 같은 요구가 나오면 그때 올린다.** 한 번은 우연이다.
`daypicker` 서브패스도 같은 자리에 있으므로, 정하면 둘 다 같은 방향으로 간다.

## 하지 않는 것

- **도메인 지식을 패키지에 넣지 않는다.** 블랙 · 문자 · 지갑 · 유저타입은 앱 것이다
- **한 프로젝트의 편의를 위해 패키지 API 를 늘리지 않는다.** **두 번째 프로젝트에서 같은 요구가
  나오면** 그때 올린다. 한 번은 우연이고 두 번은 공통분모다
- **경계를 무르게 하지 않는다.** `hooks` / `route-meta` / `axios` 는 서로를 import 하지 않고,
  런타임 정책은 옵션으로 주입받는다. 적용이 급하다고 여기를 열면 라이브러리가 아니게 된다
- **패키지를 고치면서 그 프로젝트 커밋에 섞지 않는다**

## 배포는 언제

**세 프로젝트 중 둘이 실제로 돌 때.** 그때는 배포 전에 정해야 할 것들의 답이
추측이 아니라 근거로 나와 있다 ([docs/README](README.md) 의 "다음 할 일" 3번).

- `removeUndefined` 의 이름 · `isTokenExpired` 의 자리 · `IApiError` 의 `I` 접두사 —
  세 프로젝트에서 실제로 불러 보면 맞는지 드러난다
- `urlKeys` 의 타입 미전파 — 진짜 쿼리 화면에서 걸리는지

**npm 은 72시간이 지나면 unpublish 가 안 된다.** 이름은 그때 굳는다.

`@txstack` 스코프가 다른 사람에게 잡혀 있지 않은지는 **적용을 시작하기 전에** 확인해 둔다 —
네 패키지 이름은 레지스트리에 없지만(404), 공개 패키지 없이 스코프만 소유하는 것도 가능하다.

```sh
npm org ls txstack
```
