# 009 · 사이트 재검수와 후속 개선 작업안

> 2026-10-15, 008 작업 반영 후 재검수.
> 대상: https://code7004.github.io/txstack/ 와 현재 저장소 코드.
> Claude가 후속 작업을 진행하기 위한 명세다. 이 문서 작성에서는 앱·패키지를 변경하지 않았다.
> 실제 진행 상태와 다음 할 일은 [README](README.md)에서 관리한다.

## 1. 결론

**홈의 제품 설명과 UI 노출은 이전보다 명확해졌다. 현재 구조를 다시 크게 바꾸지 않는다.**
첫 화면에 실제 팀원 관리 UI가 있고, 기능군별 시연·토큰 체험·패키지 선택 안내가 이어진다.
route-meta는 설정 코드와 GNB·사이드바를 함께 보여 주므로 라이브러리의 대표 장점으로 드러난다.

다음 단계는 기능 추가보다 다음 다섯 가지를 다듬는 일이다.

1. 현재 설치 경로에 맞는 실행 환경 안내
2. 모바일 첫 화면의 설명 압축
3. route-meta 시연에서 변경점 강조와 실행 가능한 예제로의 연결
4. 프로젝트 사례와 Profile
5. 직접 링크의 HTTP 상태와 페이지별 공유 정보

## 2. 확인한 것과 확인하지 않은 것

배포 사이트를 브라우저로 열어 홈과 Getting Started를 확인하고 현재 소스·CI 설정·검증 기록을 읽었다.
홈은 좁은 화면과 넓은 화면의 스크린샷을 확인했다. 모든 기기·브레이크포인트를 검사한 것은 아니다.

| 항목                 | 확인 내용                                                     |
| -------------------- | ------------------------------------------------------------- |
| 홈                   | UI 실물, 기능군, 패키지 선택, 배포 전 설치 안내가 노출됨      |
| route-meta 메뉴 추가 | GNB와 사이드바에 리포트가 함께 추가됨                         |
| route-meta 뷰어 전환 | 양쪽 메뉴에서 설정 항목이 사라짐                              |
| Getting Started      | 페이지 이동과 설치·첫 화면 코드 안내 확인                     |
| 로그 마스킹          | 오류·중첩 값·URL 쿼리 대응 코드 반영 확인                     |
| 패키지 소비자 검증   | `scripts/verify-packages.mjs`와 소비자 fixture 존재 확인      |
| CI                   | 패키지 빌드·검사·소비자 검증을 배포 조건으로 연결한 설정 확인 |
| 번들·폰트 개선       | 지연 로딩 등 변경과 README의 이전 검증 기록 확인              |

이번 재검수에서는 `pnpm check`, 패키지 소비자 검사, 사이트 빌드 전체를 다시 실행하지 않았다.
README의 성능 수치는 이전 작업의 기록이며 이번에 새로 측정한 결과가 아니다.
직접 링크의 HTTP 404는 README에 기록된 미해결 항목을 확인한 것이며 이번 브라우저에서
응답 헤더를 새로 측정하지 않았다. 후속 작업에서 변경 전후를 직접 검증한다.

## 3. 작업 1 — 시작하기의 실행 환경 안내 수정

### 문제와 근거

- `apps/site/src/pages/Start.tsx`는 `Node 20 이상`으로 안내한다.
- 현재는 npm 배포 전이라 저장소를 clone하고 `pnpm install && pnpm build`하는 절차다.
- 루트 `package.json`의 Node engines와 `.nvmrc`는 `24.14.0`이다.

소비자 앱의 지원 범위와 저장소 자체를 빌드하는 환경이 섞여 있다. 현재 안내만 따르면
독자가 저장소의 요구 조건과 다른 Node로 빌드할 수 있다.

### 작업

- **소비자 앱 환경**과 **txstack 저장소 빌드 환경**을 구분한다.
- 현재 `.tgz` 설치 절차에는 저장소 요구 Node·pnpm 버전 확인 및 전환 방법을 안내한다.
- 소비자 지원 버전은 실제 검증 범위와 패키지 조건을 확인해 적는다. 단순히 모든 안내를
  Node 24 전용으로 바꾸거나, 검증 없이 Node 20 전체 지원을 단정하지 않는다.
- 버전 확인 블록·설치 블록·문제 해결 설명을 일치시킨다.
- `pnpm create vite`가 선택하는 버전의 요구 환경도 구현 시 공식 문서와 확인한다.

### 완료 기준

- 처음 따라 하는 사람이 어떤 환경에서 clone·설치·빌드를 해야 하는지 알 수 있다.
- 문서의 버전과 `.nvmrc`·engines가 충돌하지 않는다.
- 소비자 지원 범위와 라이브러리 개발 환경이 구분되어 있다.

## 4. 작업 2 — 모바일 첫 화면 압축

### 문제

좁은 화면에서는 제목·두 문단 설명·버튼·설치 안내 뒤에 대표 UI가 나온다.
기능은 잘 설명하지만 실물을 보기까지 읽을 분량이 많다. `(UI & HOOK)`는 줄 수를 늘리며,
route-meta와 HTTP까지 포함한 구성을 충분히 설명하지 못한다.

### 작업

제목과 핵심 설명을 아래 방향으로 줄인다. 실제 문구는 화면에서 길이와 의미를 확인해 다듬는다.

> **관리 화면을 만드는 React UI와 도구**
>
> 폼·표·모달·레이아웃을 조립하고, 라우트 설정 하나로 GNB와 사이드바를 관리하세요.

- `(UI & HOOK)`를 제거하고 본문에서 패키지 구성을 설명한다.
- UI와 route-meta의 두 강점은 짧은 소개 안에 유지한다.
- CSS 변수·URL 상태·HTTP의 상세 설명은 해당 하위 섹션으로 분산한다.
- `UI 둘러보기`와 `시작하기` 두 주요 행동, npm 배포 전 안내는 유지한다.
- 실물을 앞당기기 위해 설명을 줄이되 모바일 글자를 과도하게 작게 만들지 않는다.
- 대표 데모나 기존 기능군을 다시 새로 만드는 작업으로 확장하지 않는다.

### 완료 기준

- 좁은 화면에서 제목·주요 행동·대표 UI의 연결이 이전보다 짧아진다.
- UI 라이브러리라는 정체성과 GNB·사이드바 구성의 장점이 함께 읽힌다.
- 390px 전후와 넓은 화면에서 줄바꿈·가로 넘침·버튼 배치를 확인한다.
- 변경 전후 화면을 비교해 사용자에게 보여 준다.

## 5. 작업 3 — route-meta 변경 효과 강조

### 유지할 것

현재 `RouteMenuDemo.tsx`의 같은 트리에서 코드·메뉴를 만들고 설정을 전환하는 방식은 유지한다.
별도의 메뉴 배열을 복사하지 않는다. 메뉴 노출 필터와 접근 제어의 구분도 유지한다.

### 작업

- `메뉴 추가` 선택 시 추가한 `reports` 코드와 양쪽의 리포트 메뉴를 짧게 강조한다.
- `이름 변경` 선택 시 label 변경 부분과 양쪽의 사용자 메뉴가 함께 바뀌었음을 보여 준다.
- 역할 전환 시 `설정 메뉴를 두 메뉴에서 숨겼습니다`처럼 결과를 짧게 안내한다.
- 강조는 색만으로 전달하지 말고 변경 설명 또는 표식을 함께 제공한다.
- 모션을 사용한다면 `prefers-reduced-motion`을 고려한다. 강조를 위해 무거운 라이브러리를 추가하지 않는다.
- 처음 보는 사람에게 `설정 한 곳 변경 → GNB와 사이드바에 반영`이라는 연결을 보여 준다.

### 코드 안내 보완

현재 `App.tsx — 연결 코드`에는 `role`, `NavLink`, `sideItem` 정의 등이 생략되어 있다.
상단 트리도 화면 element를 생략한 메뉴 중심 예제다.

- 발췌 코드임을 명시하고, 그대로 붙여 실행하는 완성 앱 코드처럼 소개하지 않는다.
- 완성 소스 또는 완성 예제가 있는 가이드로 바로 연결한다. 링크된 위치에서 실제로
  필요한 정의와 화면 element까지 확인할 수 있는지 검증한다.
- 홈에서 긴 완성 파일을 모두 펼치지 않는다. 핵심 설정과 연결 방식의 이해를 우선한다.

### 완료 기준

- 메뉴 추가·이름 변경의 코드와 양쪽 메뉴 변경점을 바로 찾을 수 있다.
- 권한 전환은 메뉴 필터 시연이라는 점이 유지된다.
- 생략된 코드와 완성 코드의 경계가 분명하고 실행 가능한 예제에 도달할 수 있다.
- 키보드 조작과 변경 결과 안내가 동작하며 불필요한 포커스 이동이 없다.

## 6. 작업 4 — 포트폴리오용 프로젝트 사례와 Profile

### 문제

라이브러리 소개는 개선됐지만 만든 사람의 설계 판단을 평가할 콘텐츠는 아직 부족하다.
현재 Profile 데이터는 비어 있으며 About 인덱스는 Profile·Contact 안내가 중심이다.
홈의 실제 서비스에서 추출했다는 설명은 About으로 연결되지만 구체적인 설계 사례로 이어지지 않는다.

### 작업

[007_about_draft](007_about_draft.md)를 바탕으로 프로젝트 사례를 구성한다.
기존 About 안에 포함할지 별도 페이지로 둘지는 기존 사이트 규약과 사용자 의도에 맞춰 정한다.
새 메뉴 체계를 대규모로 만들지 않는다.

1. **문제:** 여러 서비스에 중복된 UI·HTTP 설정, 라우트와 메뉴의 별도 관리
2. **판단:** 패키지 경계와 서비스 정책을 앱에 남긴 이유
3. **대표 사례:** route-meta로 라우터·GNB·사이드바·현재 위치의 정의를 모은 과정
4. **해결 과정:** 실제 결함 2~3건의 원인·수정·회귀 검증
5. **증거:** 동작 예제·코드·테스트와 연결
6. **한계:** 실제 소비자 적용, 지원 범위 등 현재 남은 검증

- 홈의 배경 설명에서 사례 본문으로 직접 이어지게 한다.
- 컴포넌트 수만 나열하지 말고 문제와 판단을 설명한다.
- 개발 시간 절감·중복 코드 감소·도입 서비스 수는 측정·확인한 사실만 사용한다.
- Profile 이름·역할·경력·연락처·링크는 사용자 제공 정보를 반영한다. 임의 작성하지 않는다.
- Contact의 기존 이슈 창구는 유지한다. 별도의 협업 연락 창구는 제공받은 정보가 있을 때 반영한다.
- 개인 정보가 없어도 저장소 근거로 작성 가능한 프로젝트 사례 작업은 진행할 수 있다.

### 완료 기준

- 처음 보는 평가자가 무엇을 왜 설계했고 어떻게 검증했는지 이해할 수 있다.
- 사례의 주장은 실제 코드·문서·동작 예제로 확인할 수 있다.
- 작성자만 확인할 수 있는 내용은 사용자 확인을 받으며 가상의 성과가 없다.
- 기존 About 초안과 실제 사이트 설명이 서로 어긋나지 않는다.

## 7. 작업 5 — 직접 링크와 공유 정보

### 현재 기록

[README](README.md)의 기존 배포 검증 기록에는 `/`·`/storybook/`은 200,
그 밖의 직접 링크는 화면 복원이 되지만 HTTP 404라는 제약이 남아 있다.
원인은 GitHub Pages의 `404.html = index.html` SPA 폴백이다.

### 작업

- 먼저 배포된 홈·문서·사례·API의 대표 경로에서 HTTP 상태와 반환 HTML을 확인한다.
- 주요 소개 페이지부터 경로별 정적 HTML 또는 사전 렌더링을 검토한다.
- Vite·React와 현재 Pages 하위 경로를 유지하면서 해결 가능한 범위를 먼저 확인한다.
  이 항목만을 위해 프레임워크 전체 이전을 전제로 하지 않는다.
- 페이지별 title·description·canonical·OG 정보를 일치시킨다.
- 포트폴리오 공유에 사용할 OG 이미지도 준비한다. 코드와 화면이 제공하는 기능에 맞게 표현한다.
- 실제 없는 경로는 올바른 404로 남긴다. 정상 페이지를 200으로 만드는 일과 구분한다.
- 모든 경로를 한 번에 처리하기 어렵다면 적용 대상과 남은 제약을 기록한다.

### 완료 기준

- 대상 페이지의 직접 링크·새로고침이 정상 상태 코드와 올바른 화면을 제공한다.
- JS 실행 전 HTML에 대상 페이지의 공유 메타데이터가 있다.
- `/txstack/` 자산 경로·내부 링크·앵커·클라이언트 이동·Storybook 연결이 유지된다.
- OG 이미지 URL과 canonical은 실제 배포 URL에 맞는다.
- 적용하지 않은 페이지의 제약을 숨기지 않는다.

## 8. 구현 순서와 범위

권장 순서는 **실행 환경 안내 → 모바일 소개 → route-meta 강조 → 사례·Profile → 공유·직접 링크**다.
작업마다 현재 코드를 먼저 확인하고 이미 반영된 내용을 중복 구현하지 않는다.

- `CLAUDE.md`, `docs/README.md`, `docs/005_site.md`, [008](008_review_and_site_plan.md)를 먼저 읽는다.
- 새로운 공개 API·패키지 추가·대규모 메뉴 변경은 이 문서의 기본 범위가 아니다.
- 시각·문구 변경에 구현을 복제하는 테스트를 만들지 않는다. 동작 결함에는 의미 있는 회귀 테스트를 추가한다.
- 실행 환경 수정은 실제 안내 절차를, UI 수정은 실제 브라우저의 작은 화면·넓은 화면·키보드 동작을 검증한다.
- 필요한 검사는 빌드와 타입 검사 순서를 지켜 실행한다. 빌드의 dist 정리와 타입 검사를 동시에 돌리지 않는다.
- 라우팅·배포 변경 시 `pnpm build`, `pnpm check`, `pnpm site:build`와 배포 경로 검증을 수행한다.
- 소비자 서비스 이관·npm publish·커밋·푸시는 별도 사용자 요청 없이 진행하지 않는다.
- 구현 결과와 미해결 항목은 README에 기록하고 이 문서에 별도 진행표를 중복 관리하지 않는다.
