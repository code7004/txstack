# 06 컴포넌트 플로우 (수직 슬라이스)

> **언제 확인하는가**: 컴포넌트·훅 하나를 작업 항목으로 잡을 때. `001` 진행의 기본 단위다.

## 1. 왜 이렇게 하는가

`packages/*` 의 기본 기능은 **이미 구현되어 있다.** 하지만 내부를 보면 불필요한 것, 결함, 개선 여지가 섞여 있다.
그래서 이 프로젝트의 실제 작업은 "새로 만들기"가 아니라 **하나씩 열어보고 정리해 올리기**다.

정리를 계층별로 하면(전부 문서 → 전부 구현 → 전부 테스트) 끝까지 가는 게 하나도 없다.
그래서 **컴포넌트 하나를 작업 항목으로 잡고, 그 하나를 끝까지 올린다.**

```
TxSpinner  ─ 문서 → 구현 → 테스트 → 스토리북 → 🧑 확인 → 문서사이트 → 에이전트 가이드 ─▶ 완료
TxButton   ─ 문서 → 구현 → 테스트 → 스토리북 → 🧑 확인 → 문서사이트 → 에이전트 가이드 ─▶ 완료
TxInput    ─ ...
```

**한 컴포넌트가 6단계와 게이트를 다 통과하면 그건 "끝난 것"이다.** 나중에 다시 열지 않는다.
그래서 **게이트를 통과하기 전에는 끝난 게 아니다** — 사람이 안 본 것을 완료로 치지 않는다.

## 2. 6단계 + 사용자 확인 게이트

| 단계   | 이름            | 산출물                                      | 양식 소유                                   | 담당            |
| ------ | --------------- | ------------------------------------------- | ------------------------------------------- | --------------- |
| **S1** | 문서 (명세)     | `docs/001_ui/components/<Name>.md`          | `001`                                       | 🤝 합의         |
| **S2** | 구현            | `packages/ui/src/<Name>/`                   | `001`                                       | 🧑 첫 / 🤖 반복 |
| **S3** | 테스트          | `packages/ui/src/<Name>/<Name>.test.tsx`    | `902`                                       | 🤖              |
| **S4** | 스토리북        | `packages/ui/src/<Name>/<Name>.stories.tsx` | [`901` 양식](../901_storybook/20_design.md) | 🤖              |
| **🧑** | **사용자 확인** | 통과 판정 또는 2차 개선 요청                | —                                           | 🧑              |
| **S5** | 문서 사이트     | 903 사이트의 해당 페이지 (Storybook 연계)   | `903`                                       | 🤖              |
| **S6** | 에이전트 가이드 | `packages/<pkg>/AGENTS.md` 의 해당 항목     | `904`                                       | 🤖              |

**job ID 는 `001-<Name>-S<번호>`** — `001-TxSpinner-S1`, `001-TxButton-S4`.
**게이트에는 job ID 가 없다.** Claude 가 여는 창이 아니라 사용자가 직접 하는 일이다.

### `S1~S4` 는 한 창에서 이어 돈다 (2026-08-25)

**1차는 통째로 🤖 의 몫이다.** 단계마다 창을 나누면 같은 코드를 네 번 다시 읽어야 하고,
S2 에서 발견한 것이 S1 문서로 되돌아가는 왕복이 잦다.

- **`S1` 의 🤝 는 그대로 남는다.** 판정이 필요한 질문은 창을 안 나눠도 그 자리에서 여쭙는다.
  파일럿에서 확정할 방침(`TxButton` 의 커스터마이징 방식 같은 것)이 특히 그렇다
- 창을 여는 프롬프트도 묶는다 — `001-TxButton-S1 ~ S4 까지 진행해줘`
- **`S5`·`S6` 는 게이트 뒤라 자연히 다음 창이다**

### 🧑 사용자 확인 — 왜 단계 사이에 있는가

`S1~S4` 는 **1차**다. 이미 있는 코드를 이관·감사·수정하고 기능을 한 번 다듬는 것까지 — 여기까지가 🤖 다.
기계가 판정할 수 있는 것(타입·회귀·계약)은 이 구간에서 전부 걸러진다.

하지만 **"내가 원하던 물건이 나왔는가"는 기계가 판정할 수 없다.** 그건 직접 만져봐야 안다.
그래서 S4 가 끝나면 멈추고, 사용자가 Storybook 에서 실제로 써 본 뒤 **2차 개선**을 요청한다.

```
S1 → S2 → S3 → S4  ─┬─▶ 🧑 확인 ─┬─ 통과 ─▶ S5 → S6 ─▶ 완료
                     │            │
                     └────────────┴─ 2차 개선 (S2~S4 를 다시 돈다)
```

- **`S5`·`S6` 가 게이트 뒤에 있는 이유**: 2차 개선에서 props 하나만 바뀌어도 사이트와 가이드를 다시 써야 한다.
  **바뀔 것을 미리 문서화하지 않는다.**
- 확인에 필요한 것은 S4 시점에 이미 다 있다 — 동작하는 구현, 회귀 테스트, 만질 수 있는 스토리.
- `ui` 가 아닌 트랙(`hooks`·`route-meta`·`network`)은 Storybook 이 없으므로 **playground·예제**로 확인한다.

게이트 표기는 나머지와 같다: 없음(미착수) · `🔄`(확인 중) · `✅`(통과) · `↩`(2차 개선으로 되돌림).

### 도구의 역할 분담 — 이것만은 헷갈리지 않는다

| 도구          | 누가 보나 | 무엇을 판정하나                                                    |
| ------------- | --------- | ------------------------------------------------------------------ |
| **vitest**    | 🤖        | 기계가 판정할 수 있는 것 — 타입, 계약, 회귀. CI 에서 자동으로 돈다 |
| **Storybook** | 🧑        | **"이게 내가 원하던 모양인가."** 사람이 직접 만져보는 자리다       |

**Storybook 을 자동 테스트로 만들지 않는다.** `play` 함수도, `@storybook/addon-vitest` 도 쓰지 않는다.
기술적으로는 가능하고 실제로 vitest 가 못 잡는 CSS 결함까지 잡지만(파일럿에서 확인함),
그렇게 하면 **사람이 볼 자리가 사라진다.** 자동 검증을 늘려야 하면 vitest 쪽을 늘린다.
근거: [901 README](../901_storybook/README.md) · [902 README](../902_testing/README.md)

### Storybook 에는 스토리가 있는 것을 전부 싣는다

한때 `main.ts` 의 `READY` 목록으로 **S4 를 끝낸 것만** 골라 실었다. **2026-08-25 에 걷어냈다** —
작업 중에 다른 컴포넌트를 못 보는 불편이 더 컸다.

**무엇이 검증됐는지는 진행 보드(`001_ui/30_tasks.md`)가 말한다.** 카탈로그가 그 역할까지 겸하지 않는다.
카탈로그에 있다고 해서 감사를 거쳤다는 뜻은 아니므로, **판단은 보드를 보고 한다.**

### S1 문서 (명세) — 가장 중요한 단계

현행 코드를 열어보고 **판정**하는 단계다. 여기서 뭘 고칠지가 결정된다. 최소 이 항목들을 적는다.

- **목적** — 이 컴포넌트가 왜 있나. 없으면 소비자가 무엇을 직접 해야 하나
- **공개 API** — props · 콜백 시그니처. `20_design.md` 의 이름 규칙을 따른다
- **커스터마이징 지점** — 어디까지 바꿀 수 있나
- **사용 예제** — 흔한 케이스 1개, 커스터마이징 케이스 1개 (복붙 가능해야 함)
- **현행 코드 감사** — **유지 / 수정 / 폐기** 판정 + 발견된 결함·불필요 코드 목록
- **하지 않는 것** — 범위 밖. 안 적으면 계속 늘어난다

> **이 파일이 그 컴포넌트에 대한 단일 진실 공급원이다.**
> S4·S5·S6 은 이걸 참조·발췌할 뿐이다. 사실이 갈리면 **여기를 고치고 나머지를 맞춘다.**

### S2 구현

S1 의 감사 결과를 실제로 반영한다. 결함 수정, 불필요 코드 제거, 명세와 시그니처 일치.
**공개 API 가 바뀌면 changeset 을 함께 쓴다** → [05_RELEASE.md](05_RELEASE.md)

### S3~S6

각 단계의 "무엇을 갖춰야 완료인가"는 그 양식 소유 트랙이 정한다 (`902` / `901` / `903` / `904`).
**양식이 확정되지 않은 단계는 파일럿에서 만든다** (§3).

## 3. 파일럿 — 기준은 실제로 한 번 해보고 정한다

지금 `901`·`902`·`903`·`904` 의 양식이 전부 미정이다. 문서로만 정하면 첫 실행에서 반드시 틀린다.
그래서 **파일럿 두 개**로 기준을 만든다.

| 파일럿              | 목적                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| **1차 `TxSpinner`** | **플로우 절차 자체를 확정한다.** 표면이 가장 작아 단계 사이의 마찰만 드러난다                              |
| **2차 `TxButton`**  | **커스터마이징 방식을 확정한다.** 손잡이가 많아 규칙이 실제로 시험됨. **콜백 이름 규칙도 여기서 확정했다** |

> **파일럿은 실제로 방향을 뒤집었다 (2026-08-25).** 둘 다 게이트를 통과한 직후,
> 스타일을 **Tailwind 클래스 문자열에서 자체 CSS 로** 바꾸기로 하면서 **둘 다 `↩` 로 되돌렸다**
> ([001_ui/20_design](../001_ui/20_design.md)). 되돌린 작업이 아깝지만 **24종에 퍼진 뒤였다면 훨씬 비쌌다.**
> 이게 파일럿을 두는 이유이고, `↩` 가 실패가 아닌 이유다 (§4).

파일럿 진행 규칙:

1. 파일럿도 **`S1`~`S4` 는 한 창, 게이트 뒤 `S5`·`S6` 는 다음 창**이다 (§2).
2. 파일럿에서 **903 문서 사이트와 904 가이드의 최소 골격도 함께 만든다.** 그게 파일럿의 목적이다.
3. 파일럿이 끝나면 산출물을 **양식으로 승격**한다 — `901/902/903/904` 의 `20_design.md` 에 "이렇게 쓴다" 로 고정.
4. 승격이 끝난 뒤에야 나머지 컴포넌트를 돌린다. **3차부터는 🤖 반복 + 사용자 리뷰.**

## 4. 진행 보드

`001_ui/30_tasks.md` 에 이 형태로 둔다. 어디까지 올라갔는지 한눈에 보이는 게 목적이다.

| 컴포넌트    | S1 문서 | S2 구현 | S3 테스트 | S4 스토리 | 🧑 확인 | S5 사이트 | S6 가이드 | 비고                  |
| ----------- | ------- | ------- | --------- | --------- | ------- | --------- | --------- | --------------------- |
| `TxSpinner` | ✅      | ✅      | ✅        | ✅        | ✅      | ⏸         | ↩         | 파일럿 1차 · 2차 통과 |
| `TxButton`  | ✅      | ↩       | ↩         | ↩         | ↩       | ⏸         | ↩         | 파일럿 2차            |
| `TxInput`   |         |         |           |           |         |           |           |                       |

표기: 없음(미착수) · `🔄`(진행중·확인중) · `✅`(완료·통과) · `↩`(2차 개선으로 되돌림) · `⏸`(보류) · `❌`(폐기)

**`↩` 는 실패가 아니다.** 게이트가 한 번도 되돌리지 않는다면 그 게이트는 일하고 있지 않은 것이다.
위 두 줄이 실제 상태다 — 파일럿 2종이 CSS 전환으로 되돌아갔다. **`S1` 은 `✅` 그대로다.**
되돌린 범위만 `↩` 로 적는다.

**`❌` 는 정당한 결과다.** S1 감사에서 "범용성이 없다" 로 판정되면 폐기하고 다음으로 넘어간다.
26종을 다 살릴 의무는 없다.

## 5. 단계를 건너뛰어도 되는 경우

- **`TxIcons` · `TxTheme` 같은 기반 모듈** — 시각 컴포넌트가 아니면 S4(스토리)를 생략할 수 있다. 대신 S5 에서 반드시 다룬다.
- **폐기(`❌`) 판정** — S1 에서 끝난다. 제거 자체는 S2 이고, 나머지 단계는 없다. **제거는 major 다.**
- 그 밖의 생략은 **사유를 비고에 남긴다.** 조용히 건너뛴 단계는 나중에 부채로 돌아온다.

## 6. ui 외 패키지에도 적용된다

작업 항목의 단위만 다르다.

| 패키지       | 작업 항목 단위                        |
| ------------ | ------------------------------------- |
| `ui`         | 컴포넌트 하나 (`TxSpinner`)           |
| `hooks`      | 훅 하나 (`useUrlQuery`)               |
| `route-meta` | 공개 기능 하나 (`buildRouteObjects`)  |
| `network`    | 공개 기능 하나 (`createClient`, 로그) |

S4(스토리북)는 `ui` 에만 해당한다. 나머지는 S5 에서 예제로 대체한다.

**🧑 확인 게이트는 전 패키지에 해당한다.** 확인 도구만 다르다 — `ui` 는 Storybook, 나머지는 playground·예제다.
S4 가 없는 트랙은 **S3 뒤가 게이트**이고, 되돌아가는 범위는 S2~S3 이다.
