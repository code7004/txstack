# 02 작업 방식

> **언제 확인하는가**: 새 세션을 열 때, 문서를 쓸 때, 담당을 판단할 때, job 을 끝냈을 때.

## 1. 대원칙 — 전체 틀은 사용자가 숙지한다

이 프로젝트는 "Claude 에게 다 만들어 달라고 하는" 프로젝트가 **아니다.**
결과물만 남고 사용자가 구조를 모르면 실패다. 만든 사람이 설명할 수 없는 라이브러리는 유지보수할 수 없다.

그래서 역할을 이렇게 나눈다.

| 담당          | 무엇을                                                                          |
| ------------- | ------------------------------------------------------------------------------- |
| 🤝 **함께**   | 요구사항 정의, 공개 API 형태, 구조 판단, 무엇을 버릴지                          |
| 🧑 **사용자** | **첫 구현** — 어떤 패턴을 이 저장소에서 처음 만드는 코드                        |
| 🧑 **사용자** | **결과물 확인** — "내가 원하던 물건인가". 아래 참고                             |
| 🤖 **Claude** | **반복 구현** — 합의된 패턴을 N번 반복. 테스트 작성, 문서 정리, 기계적 리팩터링 |

### 🧑 결과물 확인은 플로우의 정식 단계다

작업 항목마다 **`S4` 뒤에 사용자 확인 게이트가 있다** → [06_COMPONENT_FLOW](06_COMPONENT_FLOW.md).
`S1~S4` 가 1차(🤖)이고, 사용자가 직접 만져본 뒤 2차 개선을 요청해야 문서화(`S5`·`S6`)로 넘어간다.

**기계가 판정할 수 있는 것과 없는 것을 도구로 갈라 놓았다.**

| 도구          | 누가 보나 | 무엇을 판정하나                                       |
| ------------- | --------- | ----------------------------------------------------- |
| **vitest**    | 🤖        | 타입 · 계약 · 회귀. CI 에서 자동으로 돈다             |
| **Storybook** | 🧑        | **"이게 내가 원하던 모양인가."** 직접 만져보는 자리다 |

그래서 **Storybook 을 자동 테스트로 만들지 않는다.** 초록 체크로 덮이면 사람이 안 보게 되고,
그 순간 게이트가 일을 멈춘다. 자동 검증을 늘려야 하면 vitest 쪽을 늘린다.

### 판정 기준: "첫 번째냐, N 번째냐"

- `TxInput` 을 처음 만든다 → 🧑 (이 패턴이 앞으로 20개 컴포넌트의 틀이 된다)
- 같은 틀로 `TxTextarea` · `TxCheckBox` 를 만든다 → 🤖 (사용자는 리뷰로 확인)
- 새 커스터마이징 방식을 도입한다 → 🤝 합의 후 🧑
- 기존 컴포넌트 26개에 같은 방식으로 스토리를 붙인다 → 🤖

### 규칙

1. **🧑 job 은 Claude 가 대신 하지 않는다.** 막히면 설명·리뷰·대안 제시까지만 한다.
2. **판단이 필요한 job 은 사용자 승인 없이 넘어가지 않는다.**
3. **설계는 예제 코드로 먼저 합의한다.** 내부 구현보다 "소비자가 어떻게 쓰는가"가 먼저다.
4. **🤖 가 만든 것도 사용자 리뷰를 통과해야 완료다.** 리뷰 없이 넘어간 코드는 나중에 부채가 된다.
5. **커밋·푸시·배포는 사용자가 명시적으로 요청할 때만.** 자동 커밋 금지.

## 2. 문서 흐름

한 주제(번호 폴더)는 네 단계로 내려간다. **앞 단계가 비었으면 뒤 단계로 가지 않는다.**

| 파일                 | 답하는 질문                       | 기재 내용                                                          |
| -------------------- | --------------------------------- | ------------------------------------------------------------------ |
| `10_requirements.md` | **무엇을 / 왜**                   | 배경·목적, 요구사항 목록, 수용 기준, 범위 밖(하지 않을 것)         |
| `20_design.md`       | **어떻게 보이는가** (소비자 관점) | 예제 코드 먼저, 공개 API 시그니처, 결정 근거, **버린 대안과 이유** |
| `30_tasks.md`        | **무엇을 하는가**                 | job 목록 (ID · 담당 · 상태 · 완료 기준)                            |
| `40_verification.md` | **제대로 됐는가**                 | 검증 항목, 재현 절차, 결과(통과/실패 + 증거). 수용 기준과 매핑     |

**스켈레톤은 미리 만들고, 내용은 순서대로 채운다.** 창을 나눠 진행하려면 열 문서가 이미 있어야 하므로
작업 항목 문서와 보드는 착수 전에 전부 생성해 둔다. 단 🤝 표시된 절은 **사용자 승인 없이 채우지 않는다.**

`20_design.md` 의 "버린 대안과 이유" 절은 생략하지 않는다. **왜 이게 아닌지를 모르면 6개월 뒤에 다시 그 길로 간다.**

### 폴더 진입점 (`README.md`)

각 번호 폴더의 `README.md` 는 **자립적이다.** 그 주제를 진행하는 데 필요한 것이 다 있어야 한다.

- 한 줄 정의 / 존재 이유
- 현재 코드 자산 (파일 위치, 뭐가 있나)
- 현재 상태와 **다음 할 일**
- 이 폴더의 문서 목록과 링크

## 3. job

- **job 은 30분~1시간 단위다.** 하나를 끝내고 커밋할 수 있어야 한다. 더 크면 쪼갠다.
- **job ID 는 `<번호>-<순번>`** — `001-01`, `002-03`, `901-02`.
- 상태 표기는 ID 앞에 붙인다: 없음(미착수) · `🔄`(진행중) · `✅`(완료) · `⏸`(보류) · `❌`(폐기)
- job 을 끝내면 `30_tasks.md` 의 상태를 갱신하고, 검증 결과를 `40_verification.md` 에 남긴다.
- **담당 열은 결과에 따라 바꾸지 않는다.** 🧑 job 을 🤖 가 했다면 그건 규칙 위반이지 기록 수정 대상이 아니다.

## 4. 세션 운영

**창 하나 = 한 항목의 한 단계.** 여러 단계를 한 창에서 몰아 하지 않는다 — 컨텍스트가 섞이고 리뷰 지점이 사라진다.

진행 보드에서 다음 항목을 골라 새 창을 연다. 첫 프롬프트는 이 형태로 충분하다.

```
docs/README.md 와 docs/001_ui/components/02_TxButton.md 를 읽고 001-TxButton-S1 진행해줘.
```

항목 문서에는 인벤토리·착수 전 판단·단계 표가 이미 있으므로, **그 문서 하나로 시작할 수 있다.**

세션을 닫기 전에 확인한다.

- [ ] `30_tasks.md` 상태 갱신됨
- [ ] 검증 실행했고 결과가 `40_verification.md` 에 있음. 실행 못 한 검증은 **이유**를 남겼음
- [ ] 공개 API 를 바꿨으면 changeset 작성됨 ([05_RELEASE.md](05_RELEASE.md))
- [ ] 폴더 `README.md` 의 "다음 할 일" 이 다음 세션에서 읽을 수 있게 갱신됨

## 5. 구현 순서 원칙

1. 도메인·요구사항이 불명확한 기능은 **playground 에 먼저** 만들어 사용 흐름을 확인한다.
2. **소비자가 어떻게 쓸지를 예제 코드로 먼저 적고**, 그 예제가 자연스러운 방향으로 API 를 맞춘다.
3. 공개 API 형태에 사용자 승인을 받은 뒤 내부 구현으로 넘어간다.
4. 패키지 경계를 넘는 변경은 **계획 문서를 먼저 갱신**한다.

## 6. temp/ 를 다루는 법

`docs/temp/` 는 이전 문서 체계다. **참고만 한다.**

- temp 의 결론을 새 판의 근거로 그대로 쓰지 않는다. 다시 판단해서 새 문서에 다시 쓴다.
- temp 에서 가져온 결정은 **출처를 밝히고 재확인했음을 표시**한다.
- 새 판이 자립하면 temp 는 삭제한다.
