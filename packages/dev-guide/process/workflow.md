# 작업 흐름 — 요구사항 → 계획 → 구현 → 검증 → 보고

> 언제 보나: 작업 하나를 시작할 때, 끝났다고 말하기 전에.

```text
요구사항 ──▶ 계획 ──▶ 구현 ──▶ 검증(QA) ──▶ 보고(필요할 때)
requirements  plans    코드     verification   reports
     └─────────── 같은 작업 번호 nnn ───────────┘
```

## 0. 작업 번호가 필요한가

| 일의 크기                                               | 문서                                        |
| ------------------------------------------------------- | ------------------------------------------- |
| 오타 · 한 줄 수정 · 의존성 올리기 · 이름 정리           | **문서 없음.** 커밋 메시지가 기록이다       |
| 결함 하나 · 작은 기능 하나 (한 번에 끝나고 판단이 없다) | `verification/` 하나에 무엇을 · 증거 · 인계 |
| 판단이 필요하거나 여러 단계 · 여러 날에 걸치는 일       | **네 단계 전부** — 아래 1~5                 |

애매하면 번호를 연다. 번호 없이 시작한 일이 커지면 그때 연다.

## 1. 요구사항 — `requirements/nnn_title.md`

**무엇을 왜 만드나.** 구현 방법은 쓰지 않는다.

| 시작                           | 끝 (다음으로 가는 조건)                                                          |
| ------------------------------ | -------------------------------------------------------------------------------- |
| 요청 · 회의 · 결함 보고를 받음 | 수용 기준(AC)마다 ID 가 있고, 미정 사항이 표시되고, **사용자가 범위에 합의**했다 |

- 수용 기준은 **확인할 수 있는 문장**으로 쓴다 — "빠르게" 가 아니라 "목록 1,000건이 2초 안에 그려진다"
- ID 를 붙인다(`AC01`). 계획 · 검증이 같은 ID 를 쓴다
- 확정 · 제안 · 미정을 구분하고, 결정에는 날짜를 붙인다

## 2. 계획 — `plans/nnn_title.md`

**어떻게 만드나.**

| 시작              | 끝                                                                          |
| ----------------- | --------------------------------------------------------------------------- |
| 요구사항이 합의됨 | 순서 · 변경 범위 · 검증 방법이 있고, **판단이 필요한 것은 사용자가 골랐다** |

- 먼저 **지금 코드를 읽고 관찰한 것**을 쓴다. 전제가 사실과 다르면 여기서 멈추고 알린다
- 단계를 `T1` · `T2` 로 나누고, 각 단계가 어느 AC 를 채우는지 적는다
- 공개 API · 화면 모양처럼 되돌리기 어려운 것은 **예제 코드로 먼저 합의**한다
- **마지막 절은 체크리스트다** — 구현하며 지워 나간다

## 3. 구현

| 시작          | 끝                                                       |
| ------------- | -------------------------------------------------------- |
| 계획이 합의됨 | 계획의 단계가 끝나고, `pnpm check` · `build` 가 통과한다 |

- **한 번에 하나.** 작업 단위 하나를 끝까지 관통한 뒤 다음으로 간다. 계층별로 몰아서 하지 않는다
- 구현 중 계획과 다른 판단이 필요하면 **멈추고 묻는다.** 옮긴 뒤에 고치면 무엇이 원본이고 무엇이 판단이었는지 흐려진다
- 계획을 바꿨으면 계획 문서를 고친다

## 4. 검증 · QA — `verification/nnn_title.md`

**했는가.** 증거로 말한다.

| 시작             | 끝                                                             |
| ---------------- | -------------------------------------------------------------- |
| 구현 단계가 끝남 | AC 마다 통과 · 실패 · 미실행이 증거와 함께 있고, 인계가 쓰였다 |

- **AC 별로** 무엇을 해서 무엇을 봤는지 — 실행한 명령 · 결과 · 화면 캡처
- **실행하지 않은 것을 했다고 쓰지 않는다.** 확인 못 한 것은 "미실행" 과 이유
- 사람이 직접 봐야 하는 것은 **사용자 확인 체크리스트**로 남긴다 — 이것이 QA 다
- 끝에 **인계**: 바뀐 것 · 남은 것 · 남은 결정 · 다음 작업 · 배포 여부

## 5. 보고 — `reports/nnn_title.md` (필요할 때만)

**밖에 건네는 문서.** 운영진 · 다른 부서 · 외부 담당자가 읽는다.

- 첫머리에 **읽는 사람**을 쓴다. 쉬운 말로, 짧게. 커밋 번호 · 코드 이름 · 파일 경로는 꼭 필요할 때만
- 증거 · 인계 · 계산 규칙은 옮겨 적지 않고 링크한다
- 진행 보고는 `reports/000_progress_report.md` 한 장을 계속 고쳐 쓴다 — 맨 위 "지금 상태", 아래로 날짜별 기록(최신이 위)
