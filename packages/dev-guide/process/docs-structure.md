# docs 폴더 구조

> 언제 보나: 프로젝트를 시작할 때, 새 문서를 어디에 둘지 정할 때.

## 1. 여섯 칸

```text
docs/
  README.md        색인 — 읽는 순서 · 작업 목록
  project/         이 서비스가 무엇인가          NN_TITLE.md    상시
  rules/           늘 지키는 개발 규약           NN_TITLE.md    상시
  requirements/    무엇을 왜 만드나 · 수용 기준   nnn_title.md   작업
  plans/           어떻게 만드나 · 체크리스트     nnn_title.md   작업
  verification/    했는가 — 증거 · QA · 인계      nnn_title.md   작업
  reports/         밖에 건네는 문서              nnn_title.md   필요할 때
CURRENT.md         지금 어디까지 왔나 (저장소 루트)
```

| 칸              | 담는 것                                                                      | 담지 않는 것                                   |
| --------------- | ---------------------------------------------------------------------------- | ---------------------------------------------- |
| `project/`      | 서비스 목적 · 화면 목록 · 데이터 · API 계약 · 서버 구조 · 운영 절차 · 로드맵 | 작업 하나의 진행 기록                          |
| `rules/`        | 프로젝트 고유의 규약 · `00_DEV_GUIDE_DIFF.md`                                | dev-guide 에 이미 있는 규칙을 옮겨 적지 않는다 |
| `requirements/` | 배경 · 범위 · 수용 기준(AC ID) · 미정 사항                                   | 구현 방법                                      |
| `plans/`        | 관찰 · 변경 범위 · 순서 · 검증 방법 · 마지막 절에 체크리스트                 | 실행 결과                                      |
| `verification/` | AC 별 증거 · 실행한 명령과 결과 · 사용자 확인 목록(QA) · 인계                | 계획                                           |
| `reports/`      | 운영진 · 다른 부서 · 외부 담당자에게 **그대로 건넬** 문서                    | 개발 인계 · 실행 증거 (링크만 한다)            |

**작업 문서를 쓰는 순서는 [workflow.md](workflow.md) 가 갖는다.**

## 2. 파일 이름 · 번호

- **상시 문서** (`project/` · `rules/`): `NN_TITLE.md` — 두 자리 일련번호 + 대문자. `03_DATA_AND_API.md`
- **작업 문서** (`requirements/` · `plans/` · `verification/` · `reports/`): `nnn_title.md` — 세 자리 작업 번호 + 소문자. `008_reply_implementation.md`
- **한 작업은 네 칸에서 같은 번호를 쓴다.** `requirements/008_…` → `plans/008_…` → `verification/008_…`
- 새 작업은 **다음 빈 번호**를 쓴다. 뜻이 달라질 만큼 커지면 새 번호를 연다
- 한 작업 안의 하위 단계는 문서 안의 절(`T1` · `T2`)로 나눈다. 파일을 쪼개야 하면 `024-2_…` 처럼 붙인다
- 진행 보고처럼 **계속 고쳐 쓰는 전달 문서**는 `reports/000_progress_report.md` 하나로 둔다
- 파일 · 폴더 이름은 영문, 본문은 한글

## 3. 저장소 루트

| 파일                      | 담는 것                                                                                   |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| `README.md`               | 무엇인지 · 설치 · 실행 명령 · `docs/README.md` 링크. 짧게                                 |
| `CLAUDE.md` · `AGENTS.md` | AI 도구가 먼저 읽는 것 — "dev-guide 를 따른다" 문단 · 프로젝트 고유 규칙 요약 · 읽을 문서 |
| `CURRENT.md`              | 지금 상태 · 진행 중인 작업 · 다음 할 일. **상태는 여기에만 쓴다**                         |

`CURRENT.md` 는 고쳐 쓴다 — 지난 상태는 git 이 갖는다. 위에 최신을 둔다.

## 4. 문서를 쓰는 법

- **첫머리에 기준일과 상태를 쓴다.** `기준일: 2026-11-17. 상태: 합의 전 제안.`
- **사실 · 결정 · 제안 · 미정을 구분한다.** 결정에는 날짜와 누가 정했는지를 붙인다 — `(2026-10-26 사용자 결정)`
- **실행한 것과 하지 않은 것을 구분한다.** 미실행 · 실패 · 통과. 빈 보고서는 완료 보고서가 아니다
- **옮겨 적지 않고 링크한다.** 같은 내용이 두 곳에 있으면 한쪽이 낡는다
- **지금과 달라진 문서는 고쳐 쓴다.** 고친 이력은 git 이 갖는다. 이력으로 남길 가치가 있는 판단만 "왜 바꿨나" 로 남긴다
- 상시 문서 첫머리에 **언제 보나** 를 한 줄로 쓴다

## 5. 색인 — `docs/README.md`

```md
# 개발 문서 색인

기준일: YYYY-MM-DD.

## 문서 구조

(1장의 표)

## 읽는 순서

- [프로젝트 개요](project/01_PROJECT_OVERVIEW.md)
- …

## 작업

### 008 — 11월 회신 반영

[요구사항](requirements/008_reply_decisions.md) → [계획](plans/008_reply_implementation.md) → [검증](verification/008_reply_implementation.md)
```

문서를 더하거나 지우면 색인을 같이 고친다. 양식: [templates/docs-README.md](../templates/docs-README.md).
